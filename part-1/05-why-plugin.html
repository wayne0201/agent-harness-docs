第 5 章 · 把系统拆成积木

组合优于构建——Agent 框架的第一性原理

第 4 章说，活的项目才配得上活的 Agent——会说话、有记性、会成长。可一个项目凭什么「活」得长久：今天加一块、明天拆一块，改而不乱？答案藏在它的身体构造里。第 1 章我们建立过一个心智模型：Agent = 模型 + 记忆 + 工具 + 循环。这四个零件，应该怎样组织在一起？是写进一个庞大的核心系统里，还是做成一块块可以随意拆装的积木？几乎所有顶级 Agent 框架都走向了后者——组合优于构建。可「怎么拼」远比看起来复杂，有三个绕不开的问题摆在所有框架面前。这一章先立起通用的骨架——可组合性的通用三问，再看 dsh 与 codex 两个标本怎么各答各的：一个把所有部件都做成插件，一个保留中央核心、只把外围做成插件。

◆本章核心问题

为什么顶级 Agent 框架不约而同走向「组合」？「插件化」到底在解决什么问题？

▶你将获得

理解「插件化 / 可组合」为什么是 Agent 框架的第一性原理；以及一把判断架构是否「真插件化」的尺子——它将成为你阅读第二篇源码时的导航仪。

5.1 复杂性的代价：为什么大系统会失控

软件系统有一条残酷的规律：它只会越来越复杂。需求在增长，功能在叠加，代码在膨胀。

但真正要命的还不是「复杂」，而是变化：模型一个月更新一版；工具想换个提供方；用户今天要这个、明天要那个。

传统系统是怎么死的？它们把代码写成一整块：改一处，牵动另一处；想换一个零件，发现它和十几个模块缠在一起。工程师给这种系统起了一个生动的名字：大泥球（Big Ball of Mud）。

想象你有一座整块的花岗岩雕塑。它精美，但你想把左臂改成打招呼的姿势——抱歉，只能敲掉重雕。大泥球就是软件界的雕塑：每一次变化，都是一次新的雕刻。

图 5-1 大泥球：模块彼此缠绕，牵一发而动全身；积木式：边界清晰，改一处只动一块。
▶记住这个判断

一个系统的寿命，不取决于它今天多好用，而取决于它能不能便宜地改变。Agent 恰恰是最「善变」的软件——因为它的世界（模型、工具、需求）每天都在变。

5.2 组合优于构建：从积木到系统

面对不断增长的复杂度，工程师只有两条路：

  • 构建（Build）——每次从零写，造一个新整体。贵、慢、不可复用。
  • 组合（Compose）——把系统拆成标准积木，用现成的积木拼出新品。便宜、快、可复用。

组合的力量来自指数：10 块积木，理论上能拼出 2¹⁰ 种组合；100 块就是 2¹⁰⁰ 种。你不需要提前造出每一种产品，只需要造好积木，需要时拼一下。汉字就是这个道理——几百个偏旁部首，组合出上万个字。

回到 Agent：第 1 章的四个零件，就是四块积木。问答助手 = 模型 + 工具；有记忆的顾问 = 模型 + 工具 + 记忆；自主 Agent = 四块全上。不同的产品，是同一套积木的不同拼法。

图 5-2 同一套积木（模型/工具/记忆/循环），拼出三种不同的产品。

科普时间：Unix 哲学——组合思想的祖师爷

组合不是新发明。1978 年，贝尔实验室的道格·麦克罗伊（Doug McIlroy）写下三条朴素的信条：

  • 每个程序只做一件事，并把它做好；
  • 程序要能互相协作；
  • 程序的输出要能成为另一个程序的输入。

它的产物就是 Unix 管道：ls | grep "agent" | wc -l——三个小程序，用一根竖线串成一条流水线。没有哪个程序「知道」整件事，但组合起来完成了整件事。

五十年过去，这套思想依然是软件世界最被验证的真理之一。Agent 框架把「小程序」换成「插件」、把「文本流」换成「事件流」，但灵魂没变：组合优于构建。

◆一句话记住本节

不要造一个新的整体，要造一套新的积木。

5.3 可组合性的通用三问：怎么拼 · 先拼谁 · 谁说了算

从「组合优于构建」到「真能拼起来」，中间还隔着三个问题。这三个问题不属于任何框架——Linux 发行版、npm 生态、微服务、Agent 框架，凡是「把系统拆成积木再拼装」的东西，都要回答它们。先记住三问，再看 dsh 与 codex 怎么各答各的。

第一问 · 怎么拼：可组合 = 时间可逆 + 空间可叠加

一块积木要「拼得进」，得同时满足两个条件：

  • 时间上可逆（temporal）——装得上，也拆得下；拆了不留残渣，不污染别处。
  • 空间上可叠加（spatial）——拼得进，也共存得了；多块积木同处一个系统，互不打架。

这两点恰恰是传统系统最常栽跟头的地方：

  • 装上容易，拆下难——全局状态被污染，拆一个带崩一片；
  • 能装能拆，不能共存——两个插件抢同一个全局变量。
条件通俗说法反面教材
时间可逆装得上，也拆得下，拆了不留残渣装上容易、拆下难（全局状态被污染）
空间可叠加拼得进，也共存得了能装能拆、不能共存（抢全局变量）
图 5-3 时间维：装载—运行—卸载—无痕，循环可逆；空间维：多个插件并存于同一个上下文。
▶一句话记住

可组合 = 时间上可逆 + 空间上可叠加。缺一条，都不算真正的可组合。

第二问 · 先拼谁：依赖决定顺序

积木之间是互相咬合的：插件 A 提供「说话的能力」，插件 B 需要它才能工作——B 就依赖 A。依赖关系一出现，「先装谁、后装谁」这个问题就自动有了答案。

装修一套房子，工头手里有一份进场清单：水电、油漆工、木工。但油漆工进场前声明：「我必须等木工做完。」于是：

  • 清单（注册顺序）是默认规则——没有约束的工人，按清单先后进场；
  • 工人的声明（依赖配置）是覆盖规则——油漆工在清单里排前面，也得让位；
  • 实际进场（激活顺序）变成：水电 → 木工 → 油漆。

更妙的是返工规则：如果水电返工，后面贴好的砖、打好的柜子都得拆掉重来。依赖不仅决定顺序，还决定了「牵一发要动多少」。

图 5-3a 进场清单（默认顺序）vs 实际进场（依赖重排）：工人的声明覆盖清单，返工时依赖者跟着重来。
▶一句话记住

注册顺序是默认规则，依赖声明是覆盖规则——先注册谁只是起点，谁依赖谁才是终局。

第三问 · 谁说了算：秩序从约定来，不从中心来

把系统拆得够细，会逼出一个更尖锐的问题：秩序从哪里来？传统架构的回答是「从中心来」——系统里总有一个不可动的核心，其他部件围着它转、依赖它存在。但中心会老化、会变成瓶颈、会出错；更关键的是，它让「可组合」打了折扣——外围零件随便换，心脏永远换不了。

另一种回答是：秩序从约定来，不从中心来。谁提供什么能力、谁依赖什么、消息怎么传递，都是大家共同遵守的协议。中心会老化，约定却可以被共同演进、被任何一个参与者重新实现。

▶一句话记住

没有中心指挥，只有约定说话。

两个标本，两种回答

三问是逃不掉的规律，答案却是设计选择。dsh 与 codex 走了两条相反的路——无特权核心与中央核心 + 插件。这正好是全书最想让你分清的一幕：哪些是必然规律，哪些只是选择。

通用三问dsh（Cordis）的回答codex（codex-rs）的回答
怎么拼注册即效应：装进来注册的一切，卸载自动撤销crate 边界：上百个 crate 一个做一件事，依赖图即装配图
先拼谁ctx 依赖注入：声明依赖，激活顺序自动重排cargo 依赖图：Cargo.toml 声明即顺序
谁说了算无特权核心：连 Agent 循环都是插件，一切皆插件中央核心仍在：core 负责编排，插件层负责扩展

dsh 枝干 · 一切皆插件（无特权核心）

dsh 把三问答到极致。谁说了算这问，它直接宣布：核心也是插件——连模型适配器、工具注册表、会话日志、甚至 Agent 循环本身，都是插件。没有谁生来特殊，特殊只意味着「被固定住了」。

图 5-3b 插件式 · 无特权核心：模型/工具/记忆/循环平起平坐、个个可替换——连 Agent 循环本身也是插件。

你的手机就是这种哲学的日常版本：预装应用和第三方应用平起平坐——卸载预装、替换默认、随时装新应用，系统都不会崩溃。反过来，一台「所有应用都焊死在系统里」的手机，你看不惯也别想换。

dsh 让「约定说话」落地，靠的是里程碑 + 广播：Agent 的一生有固定的里程碑——出生、干活前、干活、干活后、出错、退役，每到一站就广播一声，谁关心谁挂耳朵（上课铃就是这个机制）。广播与监听的代码实现，第 15 章展开。

◆一把尺子：真插件化的试金石

它敢不敢把自己的心脏（比如 Agent 循环）也做成插件？dsh 敢。不需要看一行源码，你就能用它给任何架构打分。

codex 枝干 · 模块化单体 + 插件（中央核心仍在）

codex 的回答是另一头：中央核心 + 插件层。它的 core crate 是那个「有特权的中心」——负责把 Agent 循环、上下文、执行编排在一起，这几样恰恰是它不肯交给插件的东西。外围能力则作为插件挂上去，由 core-plugins 这个插件管理器统一加载（manifest / loader / marketplace 市场机制）。

图 5-3c codex 的中央核心 + 插件层：core 负责编排（循环/上下文/执行），外围能力由 core-plugins 挂载扩展。

它没有把心脏做成插件——但它的「可组合」体现在另一个维度：codex-rs 是一个有上百个 crate 的 workspace，一个 crate 只做一件事（apply-patch、sandboxing、execpolicy、guardian…），边界清晰到可以单独编译、单独测试。cargo 依赖图就是它的装配图。

所以「谁说了算」这问：dsh 拆掉了中心，codex 保留了中心——区别不是对错，而是把可替换的边界放在哪：dsh 放在「每个部件」，codex 放在「插件层」。

◆设计选择 vs 必然规律

三问（怎么拼 / 先拼谁 / 谁说了算）是必然规律——任何可组合系统都要回答。怎么答（无特权核心 vs 中央核心）是设计选择——两个标本，两种答案。分得清这一层，你读任何框架源码都不会被某个框架的「独特主张」绑架。

5.4 从「写代码」到「装配能力」

接受这套哲学，工程师的角色就变了：不再把一切写死，而是当积木的设计师 + 装配工——日常工作是一条流水线：

  1. 理解需求；
  2. 挑选现成插件；
  3. 写一个薄薄的自定义插件；
  4. 装配、调试、交付。

这件事和你的身份直接相关：大部分能力能「拼」出来，一个人才能跑完整个闭环——不用先造出每个零件（乐高说明书小孩也看得懂：零件是现成的）。第 6 章展开。

旧思维新思维
遇到需求从头写一个系统先找现成积木
修改功能改核心代码，牵一发动全身换 / 加一个插件
出问题排查全局，回滚版本拆掉可疑插件，回到原样
能力积累代码库越来越大积木库越来越厚
身份实现者装配师 + 积木设计师
▶预告

第 6 章将讲清为什么这个新角色叫「全链路工程师」；而第二篇会带你钻进两个标本的源码：dsh 看「注册即效应」「无特权核心」如何落地（ctx、事件、接缝，一样一样兑现），codex 看「中央核心 + 插件层」如何组织（crate 边界、插件市场）。

一张图总结

图 5-4 第五章的完整脉络：为什么（大泥球）→ 怎么办（组合）→ 通用三问 → 双标本两种回答。

要点回顾

  • 软件系统的复杂性与变化永远在增长，整块式的「大泥球」会因改不起而死亡。
  • 出路是组合优于构建：造积木、拼积木，让 N 块积木覆盖指数级的可能性。
  • 可组合性有三问，与任何框架无关：怎么拼（时间可逆 + 空间可叠加）、先拼谁（注册顺序默认、依赖声明覆盖）、谁说了算（秩序从约定来，不从中心来）。
  • 三问是必然规律，答案却是设计选择：dsh 把核心也做成插件（一切皆插件 / 无特权核心）；codex 保留中央核心、只把外围做成插件（模块化单体 + 插件层）。
  • 工程师的角色随之改变：从「把一切写死」到「设计积木 + 装配能力」——这是全链路工程师的第一块基石。

动手做

这一章同样不需要写代码，只需要「看」与「想」：

  1. 找一个：打开你常用的某个软件，列出它的「可替换部分」与「焊死部分」。如果把它重构成「一切皆插件」，哪个部分最难拆？为什么？
  2. 拼一次：用第 1 章的四个积木（模型 / 工具 / 记忆 / 循环），设计两个「不同的产品」（比如一个客服机器人、一个代码审查助手），写出它们各自用了哪几块积木。
  3. （可选）看一眼：打开 deepseek-harness 仓库的 packages/ 目录——四十多个包，一个包只做一件事；再打开 codex 的 codex-rs/——上百个 crate，一个 crate 一件事。感受「一个包一件事」在两种架构里各自的长相。
