第 5 章 · 把系统拆成积木

组合优于构建——Agent 框架的第一性原理

第 4 章说，活的项目才配得上活的 Agent——会说话、有记性、会成长。可一个项目凭什么「活」得长久：今天加一块、明天拆一块，改而不乱？答案藏在它的身体构造里。第 1 章我们建立过一个心智模型：Agent = 模型 + 记忆 + 工具 + 循环。这四个零件，应该怎样组织在一起？是写进一个庞大的核心系统里，还是做成一块块可以随意拆装的积木？DeepSeek Harness 的回答斩钉截铁：一切皆插件——连模型适配器、工具注册表、会话日志、甚至 Agent 循环本身，都是插件。这一章，我们回答它为什么这么选。

◆本章核心问题

为什么顶级 Agent 框架不约而同走向「组合」？「插件化」到底在解决什么问题？

▶你将获得

理解「插件化 / 可组合」为什么是 Agent 框架的第一性原理；以及一把判断架构是否「真插件化」的尺子——它将成为你阅读第二篇源码时的导航仪。

5.1 复杂性的代价：为什么大系统会失控

软件系统有一条残酷的规律：它只会越来越复杂。需求在增长，功能在叠加，代码在膨胀。

但真正要命的还不是「复杂」，而是变化：模型一个月更新一版；工具想换个提供方；用户今天要这个、明天要那个。

传统系统是怎么死的？它们把代码写成一整块：改一处，牵动另一处；想换一个零件，发现它和十几个模块缠在一起。工程师给这种系统起了一个生动的名字：大泥球（Big Ball of Mud）。

想象你有一座整块的花岗岩雕塑。它精美，但你想把左臂改成打招呼的姿势——抱歉，只能敲掉重雕。大泥球就是软件界的雕塑：每一次变化，都是一次新的雕刻。

图 5-1 大泥球：模块彼此缠绕，牵一发而动全身；积木式：边界清晰，改一处只动一块。
▶记住这个判断

一个系统的寿命，不取决于它今天多好用，而取决于它能不能便宜地改变。Agent 恰恰是最「善变」的软件——因为它的世界（模型、工具、需求）每天都在变。

5.2 组合优于构建：从积木到系统

面对不断增长的复杂度，工程师只有两条路：

  • 构建（Build）——每次从零写，造一个新整体。贵、慢、不可复用。
  • 组合（Compose）——把系统拆成标准积木，用现成的积木拼出新品。便宜、快、可复用。

组合的力量来自指数：10 块积木，理论上能拼出 2¹⁰ 种组合；100 块就是 2¹⁰⁰ 种。你不需要提前造出每一种产品，只需要造好积木，需要时拼一下。汉字就是这个道理——几百个偏旁部首，组合出上万个字。

回到 Agent：第 1 章的四个零件，就是四块积木。问答助手 = 模型 + 工具；有记忆的顾问 = 模型 + 工具 + 记忆；自主 Agent = 四块全上。不同的产品，是同一套积木的不同拼法。

图 5-2 同一套积木（模型/工具/记忆/循环），拼出三种不同的产品。

科普时间：Unix 哲学——组合思想的祖师爷

组合不是新发明。1978 年，贝尔实验室的道格·麦克罗伊（Doug McIlroy）写下三条朴素的信条：

  • 每个程序只做一件事，并把它做好；
  • 程序要能互相协作；
  • 程序的输出要能成为另一个程序的输入。

它的产物就是 Unix 管道：ls | grep "agent" | wc -l——三个小程序，用一根竖线串成一条流水线。没有哪个程序「知道」整件事，但组合起来完成了整件事。

五十年过去，这套思想依然是软件世界最被验证的真理之一。Agent 框架把「小程序」换成「插件」、把「文本流」换成「事件流」，但灵魂没变：组合优于构建。

◆一句话记住本节

不要造一个新的整体，要造一套新的积木。

5.3 Cordis 的哲学内核：时空 · 依赖 · 无特权核心

DeepSeek Harness 的底层框架叫 Cordis——一个开源的插件元框架。它的设计论文《A Programming Paradigm for Spatiotemporal Composability》（时空可组合性的编程范式）与源码仓库（cordiverse/cordis）都是公开的。把论文标题拆开，Cordis 的哲学内核是三件事：怎么拼、先拼谁、谁说了算。

怎么拼：时空可组合性

  • 时间维（temporal）：装得上，也拆得下。插件装载时注册的一切（服务、事件、效应），在卸载时自动撤销，不留残渣。
  • 空间维（spatial）：拼得进，也共存得了。多个插件能同时待在同一上下文里，互相提供能力、消费能力。

这两点为什么难？传统插件系统有两样通病：

  • 装上容易，拆下难——全局状态被污染；
  • 能装能拆，不能共存——两个插件抢同一个全局变量。

Cordis 的对策是四个字——「注册即效应」：装载时注册的一切，卸载时自动撤销。这四个字的分量，第 14 章会展开讲。

图 5-3 时间维：装载—运行—卸载—无痕，循环可逆；空间维：多个插件并存于同一个上下文。
时间维 ✓ 能拆时间维 ✗ 拆不掉
空间维 ✓ 能并存Cordis：一切皆插件 ✅焊死的整体式系统
空间维 ✗ 不能并存卡带式：一次只能插一个大泥球：拆不动也拼不上
▶一句话记住

可组合 = 时间上可逆 + 空间上可叠加。缺一条，都不算真正的可组合。

先拼谁：依赖

组合还有一个容易被忽略的维度：积木之间是互相咬合的。插件 A 提供「说话的能力」，插件 B 需要它才能工作——B 就依赖 A。依赖关系一出现，「先装谁、后装谁」这个问题就自动有了答案。

装修一套房子，工头手里有一份进场清单：水电、油漆工、木工。但油漆工进场前声明：「我必须等木工做完。」于是：

  • 清单（注册顺序）是默认规则——没有约束的工人，按清单先后进场；
  • 工人的声明（依赖配置）是覆盖规则——油漆工在清单里排前面，也得让位；
  • 实际进场（激活顺序）变成：水电 → 木工 → 油漆。

更妙的是返工规则：如果水电返工，后面贴好的砖、打好的柜子都得拆掉重来。依赖不仅决定顺序，还决定了「牵一发要动多少」。

图 5-3a 进场清单（默认顺序）vs 实际进场（依赖重排）：工人的声明覆盖清单，返工时依赖者跟着重来。

换成插件的语言，就是前面说的那个例子：注册顺序是 C → B → A（C 无依赖，B 声明依赖 llm，A 提供 llm），激活顺序却是 C → A → B。清单没有被推翻，只是被依赖重排了。（这套机制怎么运转，第 14 章展开。）

▶一句话记住

注册顺序是默认规则，依赖声明是覆盖规则——先注册谁只是起点，谁依赖谁才是终局。

谁说了算：无特权核心

「一切皆插件」走到极致，会逼出一个更尖锐的问题：「核心」本身，算不算插件？传统架构的回答是「不算」——系统里总有一个不可动的中心，其他部件都围着它转、依赖它存在。这个中心，就是特权核心（privileged core）。

特权核心的存在，让「可组合」打了折扣：外围零件随便换，心脏永远换不了。这就像一套乐高，所有积木都能拆，唯独中间那块被焊死了——于是每一块都被它绑架。

「一切皆插件」的哲学推论只有一个：核心也必须是一个插件。没有谁生来特殊，特殊只意味着「被固定住了」。

这个主张带来三个概念级的自由：

  • 可替换（自由）——任何一个部件，包括心脏，都可以被换掉：系统获得进化的自由。
  • 可扩展（生长）——新能力不需要「中心的批准」，装上就能活：系统获得生长的自由。
  • 可回滚（安全）——任何部件都可以安全拆下：系统获得试错的自由。
图 5-3b 传统架构：所有模块围着不可动的核心；插件式：部件平起平坐，个个可替换。

你的手机就是无特权核心的日常版本：预装应用和第三方应用平起平坐——卸载预装、替换默认、随时装新应用，系统都不会崩溃。想象一台「所有应用都焊死在系统里」的手机，你就理解了特权核心的世界。

更进一步的问题是：拆掉了特权核心，秩序从哪里来？答案是——从约定来，而不是从中心来。插件世界里的秩序是「协议」：谁提供什么能力、谁依赖什么、消息怎么传递，都是大家共同遵守的约定。

原来由中心做的决定，现在由约定来做。中心会老化、会变成瓶颈、会出错；约定却可以被共同演进，被任何一个参与者重新实现。

秩序怎么落地：里程碑与广播

「约定说了算」落到运行时，是一个朴素到不能再朴素的机制：里程碑 + 广播。Agent 的一生有固定的里程碑——出生（装配完成）、干活前、干活后、出错、退役（卸载）。每到一个里程碑，系统就广播一声，不点名任何人；谁关心这件事，谁就事先挂好自己的耳朵——听到就动手，没兴趣就当没听见。

图 5-3c 生命周期六站：出生 → 干活前 → 干活 → 干活后 → 出错 → 退役，每站响一声铃，插件各自挂耳朵。

学校里的上课铃就是这个机制：铃不叫某位老师，铃一响，各教室自己就位——新插件挂个耳朵就能参与（可扩展），拆掉插件就是摘掉耳朵（可回滚），心脏也只是打铃的人之一（可替换）。

这些里程碑在科学篇都有自己的学名：第 8 章（开工前注入指令）与第 10 章（压缩查水位）已经响过两回铃；广播与监听的代码机制，第 15 章《让零件通风报信》正式展开。哲学篇这里只记住一件事：没有中心指挥，只有里程碑说话。

◆一把尺子：真插件化的试金石

它敢不敢把自己的心脏（比如 Agent 循环）也做成插件？dsh 敢。不需要看一行源码，你就能用它给任何架构打分。

◆三件事，一张完整图景

怎么拼，看时空可组合性；先拼谁，看依赖；谁说了算，看无特权核心——殊途同归：约定说了算。

▶想进一步了解？

可以先读它的设计论文（github.com/cordiverse/paper）。这套哲学在 dsh 的代码里长什么样——五个关键词、顺序与依赖在第 14 章，消息如何流过一个个可替换的工位在第 15 章；哲学篇只负责让你先相信：没有中心，才是最强的中心。

5.4 从「写代码」到「装配能力」

接受这套哲学，工程师的角色就变了：不再把一切写死，而是当积木的设计师 + 装配工——日常工作是一条流水线：

  1. 理解需求；
  2. 挑选现成插件；
  3. 写一个薄薄的自定义插件；
  4. 装配、调试、交付。

这件事和你的身份直接相关：大部分能力能「拼」出来，一个人才能跑完整个闭环——不用先造出每个零件（乐高说明书小孩也看得懂：零件是现成的）。第 6 章展开。

旧思维新思维
遇到需求从头写一个系统先找现成积木
修改功能改核心代码，牵一发动全身换 / 加一个插件
出问题排查全局，回滚版本拆掉可疑插件，回到原样
能力积累代码库越来越大积木库越来越厚
身份实现者装配师 + 积木设计师
▶预告

第 6 章将讲清为什么这个新角色叫「全链路工程师」；而第二篇会带你钻进 dsh 源码，看「注册即效应」「无特权核心」如何在代码里落地——ctx、事件、接缝，一样一样兑现。

一张图总结

图 5-4 第五章的完整脉络：为什么（大泥球）→ 怎么办（组合）→ dsh 的答案（一切皆插件）。

要点回顾

  • 软件系统的复杂性与变化永远在增长，整块式的「大泥球」会因改不起而死亡。
  • 出路是组合优于构建：造积木、拼积木，让 N 块积木覆盖指数级的可能性。
  • Cordis 的哲学内核是三件事：怎么拼（时空可组合性）、先拼谁（依赖）、谁说了算（无特权核心）——最终是约定说了算。
  • dsh 没有特权核心：模型、工具、记忆、循环全是插件，全可从配置替换——带来可替换、可扩展、可回滚。
  • 工程师的角色随之改变：从「把一切写死」到「设计积木 + 装配能力」——这是全链路工程师的第一块基石。

动手做

这一章同样不需要写代码，只需要「看」与「想」：

  1. 找一个：打开你常用的某个软件，列出它的「可替换部分」与「焊死部分」。如果把它重构成「一切皆插件」，哪个部分最难拆？为什么？
  2. 拼一次：用第 1 章的四个积木（模型 / 工具 / 记忆 / 循环），设计两个「不同的产品」（比如一个客服机器人、一个代码审查助手），写出它们各自用了哪几块积木。
  3. （可选）看一眼：打开 deepseek-harness 仓库的 packages/ 目录——四十多个包，一个包只做一件事。感受那种「一切都是包、一个包一件事」的 Unix 气质。
