第 13 章 · Agent 是怎么拼起来的

把 Agent 的身体摊开：器官 · 组织 · 分工 · 血流。

第二幕里，你用它写代码、读黑匣子、调记忆、用技能、校准信任——它已经是个能干的同事了。第三幕开始，把它翻过来：这位同事的身体是怎么拼起来的？第 1 章的心智模型（模型 + 记忆 + 工具 + 循环），在代码架构里长成了什么器官；第 5 章说「一切皆插件」——这里看它的代码形态。

◆本章核心问题

哪些目录是 Agent 的关键节点？插件怎么管理、上下文与模型由谁负责、一次完整的工作链路怎么走？

◆全书心法 · 代码架构

一切皆插件，器官都是可换的。

心智模型的四个部件，各有一批插件在值班。

13.1 关键节点：心智模型的器官图

第 1 章的心智模型——模型（思考）、记忆（上下文）、工具（行动）、循环——在 dsh 的代码里，每一个部件都住在一批目录里。先认关键节点：

图 13-1 关键节点地图：入口、中枢、思考、行动、记忆、底座——心智模型的每个部件都有家。

一眼记住五个字：中枢、思考、行动、记忆、底座。中枢 core/ 是产品主干（agent、agent-loop、session、system-prompt、tools 都在这），思考靠 llm/，行动靠一批能力插件，记忆靠 session + context + compaction，底座是 vendored 进来的 Cordis。还有一位看门的——guard/，管循环卫生与工具超时。

13.2 插件如何管理：Cordis 的上下文

这些器官不是硬编码拼起来的。底座 vendor/ 里 vendor 了 Cordis——「一切皆插件」的内核（第 5 章的哲学，这里是它的代码形态）。所有插件，都挂到一个共享的 Context 上，它提供三样东西：

  • 服务——每个服务挂在一个稳定的 ctx.xxx 键上（ctx.llm、ctx.tools、ctx.sessions…），插件按「键」找服务；
  • 类型化事件——插件之间靠事件通信，五种派发模式各司其职；
  • 可逆效应——一切注册都通过 ctx.effect() / ctx.on() 进行，卸载时全部收回。
图 13-2 Cordis 的骨架：插件把服务、事件、效应注入共享的上下文，卸载时全部收回。

插件一多，顺序就是问题。Cordis 用两条规则回答：注册顺序是默认规则，依赖声明是覆盖规则——谁先谁后由框架算出来，不靠人肉排。这套机制是第 14 章的主角（事件派发的五种模式见第 15 章），这里先记住轮廓。

▶延伸阅读

想进一步了解 Cordis：设计论文 github.com/cordiverse/paper；源码仓库 github.com/cordiverse/cordis；dsh 的入门文档 deepseek-harness/docs/cordis-primer.zh.md。第 14 章会带你亲手写一个插件。

13.3 上下文与模型：插件分工

回到心智模型。四个部件在 Context 上各就各位：

图 13-3 agent-loop 是心脏：通过 ctx.llm 思考、通过 ctx.tools 行动、把过程写进 ctx.sessions，提示由 system-prompt 装配。
心智模型部件关键包一句话作用
模型（思考）packages/llm与模型交互的接口与适配器
记忆（上下文）session + context + compaction会话持久化、请求上下文、压缩
工具（行动）shell · fs · web · skill · lsp · subagent…各种能力，即模型的手
循环packages/core 的 agent + agent-loop「想—做—看—再想」的主循环

agent-loop 是心脏，这句不是比喻——它向框架声明的依赖，源码里写得明明白白：

// packages/core/agent-loop/src/index.ts
static inject = ['agents', 'sessions', 'llm', 'tools', 'systemPrompt']

这五样就是主流程，各挂一个 ctx.xxx 键：

依赖服务键提供插件它还要什么
agentsctx.agentsdsh-agenttypert
sessionsctx.sessionsdsh-sessiontypert
llmctx.llmdsh-llm—（背后挂适配器）
toolsctx.toolsdsh-toolssystemPrompt
systemPromptctx.systemPromptdsh-system-prompt—

主流程里 agents 和 agent-loop 是一对互补——别把它们当成同一个东西：

  • agent（dsh-agent）= 注册表：提供 ctx.agents 服务，负责「记账」——跟踪哪些 agent 活着、谁来当工厂。它自己不会跑 agent，只认一个 AgentFactory 接口（找不到工厂时它报错：no agent factory registered）；
  • agent-loop（dsh-agent-loop）= 引擎：实现 AgentFactory，在 apply 时把自己注册成工厂，然后真正把 ReactLoopAgent（想—做—看 的循环）转起来。

所以是引擎找注册表、注册表认引擎——agent-loop 声明 inject: ['agents', …]（要注册表可用），再把 setFactory(this) 填进注册表。注册表不依赖具体引擎，这正是「接口（AgentFactory）最重要」的又一个活例。

所以「最少要哪些插件才能跑起一个 Agent」的答案，就是这条主干加一个叶子 typert——agent-loop + agent + session + llm + tools + system-prompt，已经能想、能看、能写日志。要真动手（行动）再加 shell 与沙箱，要记得住（记忆）再加 session 持久化与上下文插件——但主流程就这么几颗，没有别的「总部」。

注意 base 组合包的注释原话：「行序不承载加载语义，激活由服务可用性驱动」——插件清单里谁先谁后不重要，框架按 inject 依赖算好图，服务就绪才激活对应插件；服务没了，依赖者自动卸载。这正是第 14 章的主角。

注意一个细节：ctx.llm 是接口，背后挂哪个模型适配器由配置说了算——这种「接口与实现分离」正是第 17 章能力接缝的主题。记忆三件套在运行时怎么协作——第 10 章；循环的心脏怎么跳——第 16 章。

13.4 一次完整的工作链路

光有器官还不够，看一次血流。假设你在 dsh 里说了一句：「帮我把这个项目的测试跑通。」这条消息依次经过六站——注意看，每一站都是什么：

  1. 记录输入——你的消息先被追加进会话日志（session 插件）。
  2. 装配提示——system-prompt 插件拼出系统提示，tools 插件附上工具清单（两个插件）。
  3. 请求模型——agent-loop 通过 ctx.llm 调用模型。它调的是接口；接口背后挂哪个模型适配器，由配置说了算（llm 适配器插件）。
  4. 执行工具——模型说「跑一下测试」，tools 插件走完执行管线，真正的命令由 shell 插件执行。
  5. 写回日志——工具结果作为事件追加进会话日志（session 插件）。
  6. 决定下一步——agent-loop 插件判断：测试还没过？回到第 3 步，再来一轮。
图 13-4 一条消息的六个环节：上面每一站都是插件，底下接线的是 Cordis——效应注册、服务取用、事件流动。

六站之间没有任何直接的互相调用——连接它们的，是底座 Cordis 的 Context：提示分区与工具清单是效应（注册上去、卸载可收回），模型调用与工具执行是服务（按 ctx.xxx 键取用），结果流动靠事件。所谓「没有特权核心」，机制上就是这句话：没有一站是必须经过的总部，接线都走在 Context 里。

现在做一次真实的「替换」：你想让 Agent 的命令在远程沙箱里执行，而不是本机。你要做的只有一件事——在配置里把本地 shell 插件换成沙箱插件。其余五个环节纹丝不动，而 Agent 的 bash、终端、LSP 会全部跟着搬进沙箱。这就是「一切皆插件」最值钱的时刻：一次替换，全产品改变。

为什么能这样？因为替换的唯一锚点是接口：消费者只通过同一把服务键（ctx.shell 这类）调接口，从不 import 具体实现——所以你在同一把键上挂一个匹配抽象接口的新实现，里面怎么写完全自由。系统不关心你的插件怎么实现，只认它挂的键和接口。这正是第 17 章《换一个器官》要展开的地基。

▶再品一遍那句话

「没有特权核心」的直观含义：在 dsh 里，你找不到一个所有请求都必须经过的总部——请求流经的每一个工位，都是一个可以单独替换的插件。

六站里每一站的细节，后续章节逐个放大：执行日志（第 9 章）、上下文与记忆（第 10 章）、插件与上下文（第 14 章）、事件驱动（第 15 章）、Agent 循环（第 16 章）、能力接缝（第 17 章）。

一张图总结

图 13-5 第十三章的完整脉络：关键节点 → 插件管理 → 分工 → 完整链路。之后各章逐个放大。

要点回顾

  • 心智模型四部件各有家：core（循环与装配）、llm（模型）、session/context/compaction（记忆）、能力插件（工具），底座是 vendored Cordis。
  • 一切皆插件的代码形态：插件挂到 Context，提供服务、事件、效应；顺序由「注册顺序 + 依赖声明」两条规则算出。
  • 分工：ctx.llm 思考、ctx.tools 行动、ctx.sessions 记忆、agent-loop 循环；它的依赖主干就是 agents · sessions · llm · tools · systemPrompt 这五颗（加个叶子 typert），就是跑起一个 Agent 的最少集合。
  • 一条消息六站，每站一个插件；站与站不直接调用，接线全走 Cordis 的 Context——效应注册、服务取用、事件流动。换掉 shell 插件，其余五站纹丝不动。
  • 第 9–16 章逐个放大：插件、记忆、事件、接缝、循环、日志……

动手做

三件小事，把这张地图变成你的：

  1. 对着地图找家：打开 packages/ 目录，按上文表格找到四个部件各自的包，给每个包写一句话点评。
  2. 走一遍链路：运行 npx @deepseek-ai/dsh web，发一条会调用工具的消息，对着图 13-4 指出你观察到的每一步。
  3. （可选）读入门：打开 deepseek-harness/docs/cordis-primer.zh.md 的「Cordis In Five Ideas」一节，为第 14 章热身。
