第 15 章 · 让零件通风报信

用事件驱动，在任意位置安全地插入逻辑

第 14 章结尾说：插件都挂上了、顺序也理顺了，可插件之间怎么说话？这一章把配电箱里的广播线路接上电。全章一个比喻：广播站——事件是广播，发出方不知道有谁在听，监听方各取所需；同一条广播有五种播报方式，选哪种本身就是一种约定。你会在任意位置安全地插入自己的逻辑，也第一次看清 dsh 的「神经系统」是怎么把零件串起来的。

◆本章核心问题

Agent 的「神经系统」如何工作？

▶你将获得

在任何位置安全地插入自定义逻辑的能力。

15.1 事件是什么：一条类型化的广播

服务支持直接调用——你想用模型就调 ctx.llm。但有些事没有明确的对象：某处「发生了点什么」，谁都可能关心。事件就是为这种事准备的：发出方不需要知道有谁在听。

看教程里的最小例子（原文见 deepseek-harness/docs/cordis-tutorial/04-events.zh.md）。一个计数服务，每 bump 一次就广播一条：

declare module '@deepseek-ai/cordis' {
  interface Context { stats: StatsService }
  interface Events { 'stats/report'(name: string, count: number): void }
}

export class StatsService extends Service {
  constructor(ctx: Context) { super(ctx, 'stats') }
  bump(name: string) {
    const next = (this.counts.get(name) ?? 0) + 1
    this.counts.set(name, next)
    this.ctx.emit('stats/report', name, next)
  }
}

别的插件想听，就登记一个监听器；它甚至不用 import 计数服务：

ctx.on('stats/report', (name, count) => {
  console.log('[stats] ' + name + ' -> ' + count)
})

解剖这条广播，四个零件：

  • 名字——'stats/report' 采用 namespace/action 约定，一看就知道是谁家的什么事；
  • 负载——name, count，事件里带的数据；
  • 类型——interface Events 声明合并（第 14 章 14.4 讲过的「说明书」这招），让名字、参数、返回值全程有类型检查——所以叫「类型化事件」；
  • 监听器——ctx.on() 登记的回调。它是效应：插件卸载时自动移除，绝不遗留 removeListener 之类的烂摊子。
图 15-1 事件解剖：发出方只管 emit，有多少听众、听众是谁，它一概不知。

先点破一层边界：框架不预置任何业务事件。Cordis 只提供「广播站 + 五种播报方式」这套机制；事件名（stats/report、tools/pre-execute、agent/request-error……）全由各插件自己声明——就是 interface Events 那行声明合并，谁想广播什么，谁在自己的代码里声明。事件由插件触发，其他插件响应；框架从头到尾不「发明」任何一条事件。

▶无特权核心，连事件都没有特权

这正是第 5 章「谁说了算」的又一次落地：事件不是框架的保留字，而是插件之间的约定。你要加自己的事件，照抄 stats 的三行（声明 interface Events、ctx.emit 触发、ctx.on 响应）即可。

▶一个编译期的小技巧

监听方要看到事件类型，写一行 import type {} from './stats.ts' 即可——它不产生任何运行时 import，只把声明合并带进类型检查。第 14 章 14.4 的「说明书」在这里派上了用场。

15.2 五种派发模式：广播还是传阅

「广播出去」只是最粗糙的一种。不同的事，需要不同的播报方式：

模式调用语义生活说法
emitctx.emit(...)同步广播；不等结果，也不收集全校广播：听见就听见
parallelawait ctx.parallel(...)所有监听器并发执行，一起等同时抄送：各干各的，都交卷
serialawait ctx.serial(...)排队执行；第一个有结果的胜出，后面停排队办事：谁能办谁办
bailctx.bail(...)serial 的同步版同上，但不排队等
waterfallctx.waterfall(...)层层包装：每人可改结果，也可短路传阅单：每人都可批注、可拦下

与其一张图塞五种，不如一种模式一张图、一段代码——每种都看清「参数怎么进、结果怎么回」，再看它适合什么活。

emit：全校广播

广播出去就好，不等、不收集返回。适合「发生了什么事」的通知：

图 15-2 emit：参数单向流出，结果不回流，发出方拿到 void。
// emit：广播出去，不等、不收集
ctx.on('ready', () => console.log('A'))
ctx.on('ready', () => console.log('B'))
ctx.emit('ready')          // A、B 都会跑；不等待；返回 void

parallel：同时抄送

广播但await——所有监听器并发跑完才继续，结果还是不收集。适合「各干各的、都要办完」：

图 15-3 parallel：并发执行、一起等，结果不收集，失败最后聚合报错。
// parallel：并发广播，等全部完成
ctx.on('warm', async () => { await sleep(100) })
ctx.on('warm', async () => { await sleep(200) })
await ctx.parallel('warm') // 两个并行跑，都完成才往下；有失败则聚合报错

serial：排队办事

按顺序逐个问，第一个返回非空值的监听器拍板，后面的不再问。适合「谁能办谁办」：

图 15-4 serial：逐个追问，第一个非空返回胜出；返回 undefined 就继续问下一个。
// serial：依次问每个人，第一个能办的拍板
ctx.on('route', async (path) => {
  if (path.startsWith('/api')) return 'api-server'  // 我处理
  return undefined                                   // 不归我管，问下一个
})
ctx.on('route', async (path) => {
  if (path.startsWith('/static')) return 'static-server'
  return undefined
})
const server = await ctx.serial('route', '/api/users')  // 'api-server'

bail：同步排队

serial 的同步版：不 await，第一个同步返回非空值的监听器立即拍板。适合「同步环境下的单决策」：

图 15-5 bail：serial 的同步版，不 await，第一个同步非空返回立即拍板。
// bail：serial 的同步版，不 await
const gate = ctx.bail('lookup', 'key')  // 第一个同步返回非空值的监听器立即拍板

waterfall：传阅单

一层包一层：参数不动（next() 不带参数），数据靠返回值从里往外层层包裹。适合「每人都要过目」的加工/拦截：

图 15-6 waterfall：参数不动，返回值从里往外层层包裹，调用方拿最外层①返回的最终值。
// waterfall：参数不动，返回值层层包裹
ctx.on('transform', async (value, next) => {
  const inner = await next()   // 打开套娃
  return '[' + inner + ']'     // 包一层
})
ctx.on('transform', async (value, next) => {
  const inner = await next()
  return inner + '!'
})
const result = await ctx.waterfall('transform', 'hi', async () => 'hi')
// result === '[hi!]' —— 调用方拿最外层①返回的包裹

五种模式的「性格」看清了，还有一个横跨所有模式的问题：监听器谁先谁后？

顺序：谁先谁后，谁说了算

监听器的排队顺序由什么决定？三层看全：

  1. 监听器之间：注册顺序——谁先 ctx.on()，谁先跑；prepend: true 是唯一的插队键，把它顶到最前（想抢先一步就加它）；
  2. 插件之间：激活顺序——插件 apply(ctx) 先执行，它的 ctx.on() 就先跑；激活顺序由第 14 章讲过的 inject 依赖声明算出来；
  3. 结论：监听顺序最终由依赖关系决定，框架不搞按优先级、按字母的花活。

这一条有个实战含义，叫顺序即权力：waterfall 里先跑的监听器先拿到 next() 链，能包住后面所有的层。想让你的拦截器抢在所有规则前面（比如最高优先级的审批），用 prepend: true；想让它排在某个依赖插件之后（比如等它先准备好），靠的是让那个插件先被激活（inject 关系）。

▶本节口诀

单向靠 emit/parallel，择一靠 serial/bail，加工靠 waterfall；先跑的先包，短路即拍板，顺序由注册与依赖说了算。

⇄双线提示 · 创造线视角

这套「短路 = 拍板」的语义，第 12 章你已经用过了——那四道关卡里 pre-execute 的「允许 / 否决 / 询问」，本质就是一次 waterfall 短路：谁想拦，谁不调 next()。机制在这，用处在第 12 章。

15.3 dsh 里的事件：观察与拦截

回到 dsh。神经系统里跑着哪些真实信号？举三个有代表性的：

  • 会话事件：session/created、session/event——会话建立时广播，每条记录追加后广播（第 9 章执行日志的主角）；
  • Agent 生命周期事件：agent/created、agent/disposed、agent/error——一个 Agent 出生、死亡、报错，全队都能听见；
  • 工具管线事件：tools/pre-execute、tools/execute、tools/post-execute——一次工具调用的前、中、后，都是 waterfall。

看工具调用这条链。模型说「帮我跑个命令」，消息走到 shell 之前要过三道关：

图 15-7 工具三连站：前、中、后三个 waterfall 事件，把「执行」变成「层层把关」。

这就是 dsh 的扩展点即事件：想给每次工具调用加日志、加限流、加审批，不用改工具本身，监听对应事件就行。再看一个串门子：模型请求失败时，agent/request-error 一响，llm-retry 立刻重试，compaction-basic 顺手压缩上下文——两个完全无关的插件，只凭同一条广播就配合起来。

这一节叫「观察与拦截」——两类事件的用法截然不同：

观察型拦截型
典型session/event · agent/created · agent/request-errortools/pre-execute · tools/execute · tools/post-execute
模式emit / parallel（广播、并发）waterfall（层层把关）
语义「发生了」——记日志、做遥测、触发后续「要不要放行」——允许 / 否决 / 替换
判断一句只关心「发生」不关心「结果」要影响「结果」或「走不走」

判断口诀：只想知道「发生了」→ 观察型（emit/parallel）；想影响「结果」或「走不走」→ 拦截型（waterfall）。想给工具调用加日志就用观察，想加审批就得用拦截。

⇄双线提示 · 应用线视角

你不写监听器，照样要读这些事件：会话出了岔子，去第 9 章的执行日志里看 session/event；工具调用不对劲，看它过没过 pre-execute 三关。

15.4 事件即文档：谁发出，谁消费

事件多了以后，最怕的是「这条广播没人听」或「这俩插件暗地里耦合」。dsh 的答案是：把事件本身当成文档。仓库里有一份自动维护的矩阵 deepseek-harness/docs/event-producer-consumer.zh.md，记着每个事件的声明位置、派发方与全部监听方——刚才 15.3 那个「串门子」（agent/request-error），它在矩阵里的完整家谱长这样：

图 15-8 一条广播的家谱：谁发出、谁在听、什么模式，矩阵里一目了然。

这份矩阵能存在，靠两个约定：事件名用 namespace/action 让「谁家的事」一眼可读；声明时用 @mode 标签写明模式，生成工具能把「声明说 emit、代码却写成 waterfall」这类错误在发布前抓出来。于是，广播线路本身就是接线图——你随时能查「我发的这条广播，现在有谁在听」。

⇄双线提示 · 两边都用

写插件前查矩阵：我要发的事件谁在听、什么模式？用 Agent 时也查矩阵：这个行为是哪个插件干的？一张表，两边查。

一张图总结

图 15-9 广播站全景：五种播报方式围着同一条广播，矩阵让广播线路成为接线图。

要点回顾

  • 事件 = 类型化的广播：名字（namespace/action）、负载、类型声明、监听器四件套；监听器是效应，卸载自动移除；事件名由各插件声明，框架不预置。
  • 五种派发模式：emit/parallel 单向、serial/bail 择一、waterfall 加工——serial 是「追问」（逐个问、第一个非空胜出），waterfall 是「套娃」（参数不动、返回值从里往外层层包裹，调用方拿最外层返回的包裹）。
  • waterfall 是拦截器：调 next() 委托下游，不调就短路；单决策事件里，短路就是拍板。
  • 顺序即权力：监听器按注册顺序排队，prepend: true 插队；插件激活顺序由 inject 依赖决定。
  • 观察 vs 拦截：只想知道「发生了」用 emit/parallel；想影响结果或走不走用 waterfall。扩展点即事件——不用改工具本身；事件即文档——矩阵可查。

动手做

  1. 打开 event-producer-consumer.zh.md，挑一条你感兴趣的事件，说出它的模式、派发方与一个监听方。
  2. 回忆一次 dsh 会话里的工具调用，按图 15-7 的三连站，说出它经过的 pre-execute / execute / post-execute 三关。
  3. 设想你要加的日志功能：它该监听哪个事件？用哪种模式？（提示：只观察用 emit，要拦截用 waterfall。）
