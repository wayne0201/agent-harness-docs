第 11 章 · 技能是这样被使用的

skills 技能库——按需拆开的一排锦囊

第 10 章结尾留了个话头：消费线还剩最机灵的一层——skills 是「按需调用」的作业指导书，Agent 什么时候想起它、怎么把它调进来。本章就把这两个问题拆开。

来历先补三句：

  • 第 7 章见过它的家——.agents/skills，11 个技能；
  • 第 8 章 8.3 见过它的出身——同一件事反复做，写回成技能；
  • 第 10 章的表里定了性——人拍板设计、Agent 常代笔，调用才读。

本章讲使用：技能库长什么样、什么时候拆、拆开后模型拿到什么、用得对不对怎么看。

◆本章核心问题

技能是什么？Agent 什么时候、怎么调用它们？拆开锦囊，模型拿到的是什么？

▶你将获得

看懂技能的调用链路——会挑、会点、会验收，知道什么该交给技能、什么还得自己盯。

11.1 技能是什么：一排锦囊

先回答一个更根本的问题：为什么不用 AGENTS.md 承载这些流程，非要单开一个技能库？因为两者是两种吃法——AGENTS.md 每次必读，技能按需调用（第 10 章口诀）。

把 11 份作业指导书全写进 AGENTS.md，每轮请求都要原文照登这 11 本手册——大部分任务只用得上其中一本：预算白花、台面被占、信号被淹没。反过来，人人该守的全局规矩塞进锦囊，又怕模型想不到去拆。

AGENTS.md技能
装什么每次都要在场的约定（短、稳）干到那步才需要的流程（长、细）
什么时候读每次开工注入，原文照登调用才读：纸条常驻，正文按需
换着放的代价11 本手册每轮照登：预算白花、信号淹没全局规矩进锦囊：怕模型想不到拆
类比员工手册，人人必读岗位作业指导书，干那活才翻

所以技能不可替代的那一点是两级结构：纸条（名字 + 用途）常驻菜单，正文（指导书）按需加载——AGENTS.md 只能整篇照登，没有「目录」这一层。这正是第 8 章 8.3 写回三去处里，技能和 AGENTS.md 各管一半的原因。

现在看技能本身。工具教的是「动作」。第 8 章 8.2 的工具说明书里，read 是读一个文件、write 是写一个文件、bash 是跑一条命令——每个工具都是一下子的动作，模型叫一次，干一件事。

可真实项目里的活大多是「流程」：提交前先看改了什么、挑出最小的测试集、跑完过了才推；审文档先查边界词、再查双语对账、最后才放行。一串有顺序、有标准的动作，靠工具说明书教不了——那就把它写成技能（skill）。

打个比方：工具是一把扳手，技能是一本作业指导书。指导书也是人写好的（第 10 章说过：skills 是人拍板设计、Agent 常代笔），放在项目的技能库里，像老师傅留的一排锦囊——遇到对应的事，拆开照着做。

图 11-1 工具是一把扳手，技能是一本指导书：一个是「一下」，一个是「一串」。

三种身份，一张表看清：

工具技能文档
身份手剧本（行军命令）地图
给什么一个动作「怎么做、什么算合格」「是什么、为什么」
什么时候上桌每次开工（说明书随请求）调用才读用到才读
例子read · write · bashdsh-pre-push-checks 等 11 个docs/architecture.md

三种身份之间还差一个「门」：

  • 技能是内容——SKILL.md 是知识，不是动作；
  • 工具是手——read / write / bash，模型直接调用；
  • skill 工具是门——技能也借一个特殊工具上桌：模型调 skill 工具（这一个动作），换来 SKILL.md 全文进上下文（这一本手册）。

执行者永远是模型 + 工具：读文档，模型变懂；拆技能，模型开始行动——但谁都不会自己跑。

▶一句话记住

工具教「手怎么动」，技能教「活怎么干」，文档告诉你「世界什么样」。

11.2 技能库：十一个锦囊贴着纸条

dsh 的技能库在 .agents/skills/，一共 11 个锦囊。每个锦囊一个目录，核心是一份 SKILL.md；锦囊外面贴着一张「纸条」——名字和用途，拆开之后，正文才是指导书本身。11 个技能各自管一摊：

  • dsh-pre-push-checks——提交 / 推送前挑出最小检查集，别整仓跑；
  • dsh-prose-standard——行文标准：文档、注释、提示词的写法与取舍；
  • dsh-doc-standards——文档的摆放、预算与双语配对；
  • dsh-translate-docs——翻译文档；
  • dsh-code-review——代码评审；
  • dsh-archive-agent-notes——归档 Agent Note（第 7 章的状态机在这里流转）；
  • dsh-doc-site-sync——文档站同步；
  • dsh-find-simplifications——找简化机会；
  • dsh-merging-stacked-prs——合并 stacked PR；
  • dsh-trim-cot-leakage——清理推理痕迹泄漏；
  • record-browser-gif——录制浏览器操作 GIF（锦囊里还自带编码脚本）。

纸条长什么样？看 dsh-pre-push-checks 的 SKILL.md 开头——「纸条」就是文件头部的 name 与 description，正文跟着展开成步骤：

---
name: dsh-pre-push-checks
description: Use before pushing, force-pushing, marking
ready for review, or claiming checks pass on a
deepseek-harness branch … to select the smallest
tests and checks that cover the outgoing diff …

# DSH Pre-Push Checks
Use this skill to run relevant local evidence once
before a deepseek-harness push …

## Inspect the outgoing change
1. Confirm the checkout and branch.
   git status --short --branch
2. Verify the live PR base or stack parent …
   pnpm --silent run change-scope --base <ref>

两处要点：纸条（description）是给模型决定拆不拆看的；正文是拆开之后照着干的。想再看一份风格不同的，dsh-prose-standard 讲的是行文判断，11.4 会用到它。

11.3 什么时候拆、怎么拆：调用链路

「按需调用」的「需」从哪来？和读 docs 一个道理，三个触发通道（第 10 章的三类触发器）：

  • 约定点名——AGENTS.md 里写「提交前用 dsh-pre-push-checks」——路牌，走到这一步就拆；
  • Agent 自判——模型看纸条（description）与任务对得上，自己决定拆；
  • 你点名——当场说「用 dsh-prose-standard 审一遍」。

三条通道汇聚到同一条调用链路：

  1. 目录上桌——随请求有一份「技能目录」：每个技能的名字 + 纸条。模型眼前等于一张菜单，这份菜单挂在 skill 工具的说明书里；
  2. 判断拆哪个——三条触发通道都汇到这里：模型选一个技能名；
  3. 调用——skill 工具按名加载，SKILL.md 正文原文进上下文（作业指导书原文照登，不摘要——和 AGENTS.md 一个规矩）；
  4. 照做——模型照着步骤出主意、工具动手（8.2 的读→写→验，在指导书的框架里跑）。
图 11-2 调用链路：菜单先上桌，判断后调用，SKILL.md 原文进上下文，模型照步骤出主意、工具动手。

走一遍真实场景：你让 Agent 往 dsh 仓库推一个改动。

  1. 约定点名——AGENTS.md 说了推送前用 dsh-pre-push-checks；
  2. 拆锦囊——SKILL.md 上桌，指导书第一条是「确认分支」，Agent 就叫 bash 跑 git status --short --branch；
  3. 照着走——第二步要「核实 PR 基线」，Agent 再叫 bash 跑 pnpm --silent run change-scope --base …，按范围挑最小测试集；
  4. 过了才推——步骤走完、证据通过，才执行推送；没过就回头修。

注意全程的节奏：指导书出主意，模型下判断，工具动手——技能没有「自动执行」，每一步还是模型叫工具完成的。

▶四个谁

谁写——人拍板设计（Agent 常代笔）；谁读——AI；谁拍板读——约定点名 · Agent 自判 · 你点名；读多少——SKILL.md 原文整篇照登。

11.4 拆开之后：照做，也要盯

拆开之后只有一句话要盯：命令会跑，判断在模型——技能的质量，直接决定「照做」的质量。三个事实：

  • 命令真的会跑——指导书写 git status --short --branch，模型就用 bash 工具真跑（11.3 场景）；「不是脚本」指不会自动跑：每步执行前模型自己判断——报错了停不停、基线不确定要不要先核实（dsh-prose-standard 原话：It is guidance, not a script）；
  • 脚本只是物料——record-browser-gif 锦囊里自带 scripts/encode_gif.py（「捆绑的编码器」），照样靠 bash 工具执行；技能机制只加载 SKILL.md 文本，不自动执行任何东西；
  • 锦囊互相援引——dsh-prose-standard 点名 dsh-doc-standards（摆放、双语对账）和 dsh-trim-cot-leakage（清理推理痕迹）；技能库是一套互相咬合的规矩，不是 11 份孤立的纸。

既然技能是人写的、模型照做的，就没有「装上就高枕无忧」这回事：

  • 用得对不对，回黑匣子查——第 9 章复盘三问：SKILL.md 上桌了吗（喂饱）· 步骤真的照做了吗（看见）· 结果有证据吗（验证）；
  • 兜底还有机器门卫——第 7 章的提交闸机、翻译校对员在流程终点等着，坏东西进不了仓库；
  • 用得不好，写回——复盘出的新经验，改技能或立新约定（8.3 写回），下次拆锦囊就更好用。
⇄双线提示 · 创造线视角

创造线的三件事，各归其位：

  • 体内实现——ctx.skills 注册提供方、skill 工具发布目录并加载 SKILL.md → 第 14 章《把功能插上插头》；
  • 自己写技能 → 第 20 章《设计一个好工具》；
  • MCP（模型上下文协议，行业标准的外部能力接入；dsh 已有 packages/mcp 早期形态）→ 第 17 章《换一个器官》。
▶回路钩子 · 用→写→长的技能线

技能线在这里闭合：同一件事反复做（8.3）→ 写回成技能（人拍板、Agent 常代笔）→ 按需调用（本章）→ 复盘验收 → 再写回。剩下的问题是：哪些环节该你点头、哪些能放心全自动——第 12 章《什么时候把钥匙交给它》。

一张图总结

图 11-3 技能全景：库房一排锦囊 → 菜单上桌 → 拆锦囊 → 照做验收——一条「用 → 写 → 长」的回路。

要点回顾

  • 工具 · 技能 · 文档：手 / 剧本 / 地图——动作、步骤、认知各管一摊；执行者永远是模型 + 工具。
  • 为什么单开技能库：约定每次必读（AGENTS.md）、流程按需上桌（技能）——11 本手册若每轮照登，预算白花、信号淹没；技能的「纸条常驻 + 正文按需」两级结构，AGENTS.md 做不到。
  • 调用四步：目录上桌 → 判断拆哪个 → skill 工具加载 SKILL.md 原文 → 模型照步骤、工具动手。
  • 三个触发通道：约定点名 · Agent 自判 · 你点名——「按需调用」的「需」就来自这里。
  • 锦囊是指导不是脚本：命令会跑（bash 工具真执行），但不会自动跑——判断在模型；写得不清照样干岔——用得对不对回黑匣子复盘；能不能放手，第 12 章讲。

动手做

  1. 打开 .agents/skills/，挑一个技能读它的 name 与 description——这行「纸条」就是模型决定拆不拆的依据；
  2. 开一个 dsh 会话，让 Agent 干一件技能覆盖的活（比如写完一段文档，让它按 dsh-prose-standard 审一遍），然后在日志里找 skill 工具的调用记录，看 SKILL.md 原文是不是上了桌；
  3. 用第 9 章复盘三问验收这次执行：喂饱了吗（SKILL.md 在上下文里吗）· 看见了什么（步骤真的照做了吗）· 验了吗（结果有证据吗）。
