第二篇 · 科学篇 应用线

第 8 章 · 让 Agent 写得出代码

项目怎么自我介绍，代码怎么写出来，约定怎么被写回

第 7 章结尾说：下一幕上手用它开发。这一章就是上手的第一步——让 Agent 写得出代码。第 3 章的心法是「上下文喂饱」，第 7 章说项目是 Agent 的外置记忆，这一章把两者接起来，补上中间一环：项目怎么把记忆喂给 Agent（交接），Agent 怎么按手册写出代码（干活），又把新经验写回项目（写回）。全章一个比喻：入职交接——项目是师傅，Agent 是那位「行业内资深、刚入职」的工程师。

◆核心问题

Agent 凭什么能看懂你的项目、写出对的代码？

▶你将获得

掌握「交接 → 干活 → 写回」三个动作——喂饱上下文、写出对的代码、让经验沉淀成约定。

8.1 交接：先让项目自我介绍

再资深的工程师，进新项目的第一天也要听交接：规矩是什么、坑在哪、怎么跑起来。项目不会说话，它的交接方式是一叠手册——第 7 章见过的那条 AGENTS.md 链。

每次会话开工，dsh 的 agent-instructions 插件（packages/context/agent-instructions）会把手册折进第一步请求，读的顺序像入职交接：

  1. 先听家规——用户全局的 AGENTS.md（家规管所有项目）；
  2. 再听项目链——从项目根目录到当前所在目录沿途的每一层，AGENTS.md / CLAUDE.md 都读（越靠当前目录的越具体）。注意读的是「路径」不是「范围」：在根下干活就只带根这一份，子目录的规矩要等你走到那里才读；
  3. 还有本地小抄——AGENTS.local.md 之类的本地 overlay，个人习惯不污染仓库；
  4. 内容完全相同的 AGENTS.md 与 CLAUDE.md 只读一次，不重复占位置。

手册们会被包进一个固定的「交接框」，再折进第一步输入：

<system-reminder>
The following workspace instructions may be relevant to your work...

Instructions from: ~/AGENTS.md
...（家规）

Instructions from: AGENTS.md
...（项目约定）
</system-reminder>
图 8-1 交接链：家规、项目链、本地小抄逐层上桌，包进交接框折进第一步请求。

一个自然的疑问：读回来的一叠手册，会被「汇总」成摘要再交给模型吗？不是——原文照登。取舍靠三个保证：内容重复的只留一份（去重）；总量超过部署时定好的预算（maxBytes）时，超出的文件被省略——是「不放进请求」，不是「压缩成摘要」；每层手册都按作用域带上。

收集、去重、预算、包框、折进第一步——这套组装流水线第 10 章《记忆是这样被读取的》统一展开，台面装不下时怎么把长历史熬成汤也在那里讲。本章记一件事：交接框紧跟在你的消息之后，一起交给模型。

走一遍例子：从一仓库文档到一条交接框

就拿本书的标本——dsh 仓库做例子。你在仓库根下干活，任务涉及 packages/core。收集和拼装是这么走的：

图 8-1b 真实收集示例：基线只带 2 份；走到 packages/core 后，packages/AGENTS.md 作为更新条补上。

开工时的基线（cwd = 仓库根）只有两份进框：家规 + 根 AGENTS.md。CLAUDE.md 与 AGENTS.md 内容完全相同 → 丢弃；README.md、docs/ 里的文档不在候选名单 → 不读——根约定里点名的 docs/architecture.md 也一样不自动带上；AGENTS.local.md 仓库里没有 → 不产生条目。

<system-reminder>
The following workspace instructions may be relevant to your work.
Use them as guidance when applicable. More specific instructions
take precedence over broader ones.

Instructions from: ~/AGENTS.md

（家规，示意）

Instructions from: AGENTS.md

DeepSeek Harness is a plugin-based agent harness on vendored
Cordis: everything is a plugin. Read docs/architecture.md
before changing packages/; follow docs/AGENTS.md for
documentation.
</system-reminder>

你说：「帮 packages/core 的 agent-loop 补个测试。」Agent 动手读、写 core 下的文件——保鲜机制发现「走到了新地盘」，把 packages/AGENTS.md 作为更新条注入；core 自己没有 AGENTS.md，不产生条目；schedule、web 不在路径上，永不读。从下一步起，模型眼前多出这一段：

Additional instructions from: packages/AGENTS.md

These package-specific rules supplement the repo-wide
conventions.

- Plugin exports: service packages default-export their service
  class; function plugins named-export name / inject / Config
  / apply and have no default export.
- Optional services use ctx.get(name). Reserve ctx. for
  declared injections…

这就是最后交给模型的样子：你的消息在前，框跟在后面；框里是原文、出处与顺序，没有一句「摘要」。这个例子里还有三条边界值得记住：

  • 没进框，不是被吞了——README、docs/ 本来就不在自动注入的候选名单里；
  • 它们是「用到才读」的资料——想让 Agent 了解某篇概念文档，把引用写进 AGENTS.md，或让它用读文件的工具自己翻；想改一个决策之前，按第 7 章分工法则的指引去翻 .agents/notes 里的「为什么」；
  • 问题只涉及一个 package 也不怕——Agent 动手读写那个子目录的文件时，保鲜机制自会把那里的手册补进来（图 8-1b 里的 ◐）；想开工前就带上，把新会话的工作目录切过去即可。

一句话：AGENTS.md 是「每次必读」的规矩，docs/ 与 notes 是「用到才读」的资料——路径外的层，走到才读。

「用到」的裁判是谁？是 Agent 自己——它判断这活缺哪份资料，就用 read 工具去翻（正是 8.2 的「模型出主意、工具动手」）；判断就有漏的可能，所以重要资料不妨把引用写进 AGENTS.md，或在消息里当场点名「先读 docs/architecture.md」。但无论点不点名，读的动作都由 Agent 用工具完成——引用不是注入，路牌不替你走路。

交接不是一锤子买卖——师傅会随时补叮嘱。Agent 每成功读写一个文件，插件就回头检查各层手册有没有新增、改动或消失，然后把更新条排进下一步输入：

  • 新增了某层 AGENTS.md → 注入「Additional instructions from: …」；
  • 内容变了 → 注入「Updated instructions from: …」，声明以新版为准；
  • 文件删了（或变成重复内容）→ 注入「Instructions removed: …」，旧叮嘱作废。

保鲜的另一个妙用，正好补上「走到地盘」的时机：你在根下、任务却在子目录时，Agent 一旦成功读写那个子目录里的文件，插件发现「走到了新地盘」，就把那里的 AGENTS.md 作为「新增」条注入——从下一步起，新规矩就在模型眼前，不用重开会话，也不用事先 cd。

图 8-2 手册保鲜：每次文件读写后回查各层手册，新增 / 更新 / 移除三种更新条排进下一步输入。
⇄双线提示 · 创造线视角

这套注入挂在「每步开工前」的一道关卡上（pre-step），插件们排着队往里塞东西——关卡和排队机制，第 15 章《让零件通风报信》展开。你做的 Agent 产品若支持 AGENTS.md，机制大同小异。

8.2 干活：手册怎么变成代码

交接上桌，师傅退到一边，新人开工。写代码不是「一口气生成」，而是读 → 写 → 验的小循环，手册立在旁边当尺子。

先交代一个底层事实：这三步不是模型「在脑子里」想完的——模型的强项是出主意，动手全靠调用工具，这正是第 1 章心智模型里「工具」那根支柱。模型每出一招，工具落实一招，结果送回模型，再决定下一招；三步不是三段冥想，而是一轮轮工具调用：

  1. 读——交接框只给了「规矩」，具体代码长什么样，Agent 动手前自己翻，靠读文件的工具（read / grep / glob）；8.1 的「用到才读」在这里兑现；
  2. 写——按手册的规矩产出改动，落盘靠写文件的工具（write / edit）。规矩不是背景板，会直接长进代码的形状里；
  3. 验——跑测试、类型检查、lint，靠执行命令的工具（bash），第 7 章的机器门卫把结果反馈回来：红了回炉再改，绿了才算落袋。

模型凭什么知道该叫哪个工具？每个工具注册时都自带一份「说明书」——名称、干什么、参数长什么样，开工时随请求一起交给模型：

// 工具自带的说明书（以 read 为例，真实描述）
name: read
description: Read a UTF-8 text file and return
             line-numbered content.
parameters: file_path / offset / limit

模型是读说明书出招的：要翻代码，就按这份说明叫 read、把路径传对。这和 8.1 是同一个道理——项目用手册让模型懂项目，工具用说明书让模型懂工具。dsh 的真规矩甚至写明：说明书要站在模型的视角写，只讲任务相关的概念，不讲人看的界面话。说明书怎么定义、怎么随请求装配——第 14 章展开。

图 8-3 写代码的小循环：读（翻源码）→ 写（按手册产出）→ 验（红了回炉）——模型出主意，工具动手，手册立在旁边当尺子。

「手册直接长进代码」听上去玄，接着 8.1 的例子看就清楚了。你在 dsh 仓库里让 Agent 动手写点东西：写一个新的工具插件，动手位置在 packages/ 下。交接框里因此多出 packages/AGENTS.md（图 8-1b 里 ◐ 的那份），它有一条真规则——函数插件必须具名导出 name / inject / Config / apply，且不得有 default 导出。Agent 产出的文件骨架，就长成规则的样子：

// 按手册规矩长出来的插件骨架
export const name = 'tool-todo'
export const inject = ['tools']
export const Config: z<Config> = z.object({ … })
export function apply(ctx: Context) { … }
// 没有 export default —— 手册明令禁止

这不是示意——packages/todo/tool-todo 现成躺在 dsh 仓库里，骨架正是这副形状。手册怎么写，代码就怎么长。

⇄双线提示 · 创造线视角

这一节站在「用」的位子上看 Agent 产出代码。这个骨架为什么必须是这四个导出、读 / 写 / 验用的工具本身怎么被插件注册进来、apply 里怎么写——第 14 章《把功能插上插头》展开。

小循环把「写得出」升级成「写得对」：「读」解决认不认识代码，「写」解决规不规矩，「验」解决跑不跑得动。每一轮工具调用都记进黑匣子——第 9 章；这个「出主意 → 动手 → 看结果」的循环怎么自动转起来——第 16 章《看心脏怎么跳》。「验」够不够、哪些环节还必须你亲自把最后一道关——第 12 章《什么时候把钥匙交给它》。

8.3 写回：用 → 写 → 长

活干完了，这一轮还差最后一步。交接是单向的——好项目会把它变成双向。第 4 章 4.4 说「用 → 写 → 长」，第 7 章管它叫成长机制——这一节看动作本身：把这次的经验写回项目。三个去处：

写回哪写什么什么时候写下次怎么被用
AGENTS.md 增补新的「怎么做」约定踩出套路、立了新规矩时交接时自动上桌（8.1）
.agents/notes「为什么」与「放弃了什么」做了有分量的决策时想改动时，先读它当初的「为什么」
.agents/skills可复用的流程（作业指导书）同一件事反复做时按需调用（第 11 章）

其中 notes 是带状态机的（第 7 章见过）：proposed 提议 → implemented 落地 / archived 归档 / rejected 否决。一条经验从「试试看」到「正式规矩」，走完这个流转才算长大。

图 8-4 写回三去处：约定进 AGENTS.md、决策进 notes、流程进 skills——下次开工全部自动上桌。
▶一句话记住

写回不是「顺手整理」，而是协作的收尾动作。每次干完活问一句：这次学到的，该写回哪里？哪怕只补一行 AGENTS.md，项目就长大一点。

8.4 回路钩子：记忆线的闭合

把记忆线完整走一遍，你会发现它是个圈：

  • 第 7 章提供——记忆放进文件（AGENTS.md、notes、skills）；
  • 本章消费——开工时交接上桌（8.1），按手册干活（8.2）；
  • 第 9 章记录——干活的过程一条条落进黑匣子（会话日志）；
  • 本章写回——经验落回文件，再被第 7 章的机制吸收，成为下一次交接的内容。
图 8-5 记忆线闭合：7 提供 → 本章消费 → 9 记录 → 本章写回 → 再被 7 吸收——一个圈。
◆全书心法 · 交接 → 干活 → 写回

交接把手册喂给 Agent，干活按手册写出代码，写回把经验存进项目。

三件事合成一条回路——这就是「项目是 Agent 的外置记忆」的完整含义。

一张图总结

图 8-6 入职交接全景：师傅手册 → 交接上桌 → 新人干活（读 → 写 → 验）→ 心得写回手册，手册越用越厚。

要点回顾

  • 交接：开工时家规 + 项目链（每层 AGENTS.md / CLAUDE.md）包成交接框折进第一步；读写文件后手册自动保鲜。
  • 干活：读 → 写 → 验小循环，模型出主意、工具动手（read / grep 读、write / edit 写、bash 验）；工具靠说明书自我介绍，手册怎么写，代码就怎么长。
  • 写回三去处：新约定进 AGENTS.md、决策进 notes（状态机流转）、流程进 skills——下次开工自动上桌。
  • 记忆线：7 提供 → 本章消费 → 9 记录 → 本章写回 → 再被 7 吸收，一个圈。
  • 一句话：交接喂饱上下文，干活写出代码，经验写回手册。

动手做

  1. 开一次 dsh 会话做个小任务：先看会话日志里的 system-reminder 段，确认手册上了桌；再观察 Agent 是不是「先翻代码 → 再产出 → 检查没过再改」，把读 → 写 → 验对一遍。
  2. 干完活后，亲手补写一条 AGENTS.md 约定（哪怕一行），下次会话观察它有没有被自动读到。
  3. 拿一次真实协作的经历做盘点：这次学到的，该写回三去处的哪一个？为什么不是另外两个？

这一章走完了「交接 → 干活 → 写回」三个动作。干活的每一步都记在黑匣子里：干岔了怎么办、黑匣子怎么读——下一章《复盘先读黑匣子》。
