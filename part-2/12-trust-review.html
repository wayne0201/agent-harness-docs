第 12 章 · 信任的分级与把关

信任不是态度，是可校准的机制

第 11 章结尾留了个话头：技能会挑了、也会验收了——剩最后一问：哪些环节该你点头，哪些能放心全自动。本章按三步走：先看完全放开的危害，再立防止危害的标准，最后看机制怎么落地。

第 8 章 8.2 埋过同一颗种子（要不要人把最后一道关），第 6 章也点过名——产出怎么查、信任怎么校准。全章一个比喻：管家与钥匙——信任分档就是钥匙分级，查账本的账本就是第 9 章的执行日志（黑匣子）；分工一句话：机器管每一刀，你管抽查与拍板。

12.1 完全放开的危害：把关全拆了会怎样

先回答最该先问的问题：为什么不能干脆「放手让 Agent 干」？把把关全拆掉，看会怎样。

做个「拆掉一个」实验——拆掉哪一道把关，就放开哪一种危害：

拆掉什么把关完全放开会怎样
沙箱（活动范围）一条命令写穿工作区、覆盖系统文件——环境当场报废
批准通道（问人）删库、强推、发布——不可逆动作直接执行，拦都拦不住
审查（账本）干错了没人知道，错产物一路滚进下游
升降级（调档）犯过错还照样全信，永远不长记性
判断权在模型外判断交给模型自觉——它会概率性犯错、可能被诱导，出了事也无人可问责

这些危害有个共同点：都发生在「影响面大、不可逆、验证不了」的动作上。所以把关要防的从来不是 Agent 这个人，是这几类动作——这正是 12.2 三问的种子。

为什么不能靠「模型自觉」兜底？因为自觉不是机制：模型会概率性犯错、可能被提示词诱导，而且它本来就没有判断权——让它自己判自己，等于没人判。把关必须长在模型外面（谁在判断，12.3 展开）。

12.2 防止危害的标准：要防住什么

危害列完，标准就从每条危害反推：要防住它，系统得达到什么。两列一一对应：

危害要防住它的标准
越界写划定活动范围：沙箱三档 read-only / workspace-write / danger-full-access
不可逆误操作危险动作必须问人：批准通道，没人应答 = 否决
静默错误产物每一步可查：账本（第 9 章执行日志）+ 收工复盘三问
信任不校准信任随战绩浮动：出错降档、连赢升档
靠自觉兜底判断权在模型之外：代码裁决 + 人拍板

标准有了，还要回答「每件活该上哪条标准」——这就靠给动作分级。分级不是一句「我信它」的态度宣言，而是一套按动作发钥匙的规矩：

档位钥匙什么活例子
全信给全套机械、可回滚、可自动验证重命名、格式化、跑测试
核查给钥匙，但查账本有影响，但过程可查、结果可验改配置、批量重构、发文档
亲为钥匙留在主人手里不可逆、影响大、判断重删库、发布、对外承诺

分档不靠感觉，靠三问：

  1. 影响面大不大？只动自己 vs 动别人、动线上；
  2. 可不可逆？改完能撤 vs 覆水难收；
  3. 可不可验证？测试能自动判定对错 vs 只有人看得出好不好。

三问都轻 → 全信；有一问重 → 核查；有一问致命 → 亲为。拿四件日常活试一遍三问：

  • 重命名本地变量、跑一遍测试 → 全信：影响小、可回滚、测试自动判定；
  • 批量改 20 个文件的函数签名 → 核查：git 可撤、测试可验，但影响不小；
  • 删掉 docs/ 里一个文件 → 核查：影响虽小，不可逆、好坏只有人看得出；
  • 往 npm 发布一个版本 → 亲为：覆水难收，只有用户知道好不好。

规律一眼可见：三问的对象永远是动作，不是这个人——同一个 Agent，跑测试可以全信，删文件就得核查。这正是第 6 章「环节越机械越交给 AI，判断越关键越留给你」的落地版。

图 12-1 三把钥匙：三问定档——都轻全信，一问重就核查，一问致命就亲为。
▶一句话记住

全信不是「它不会错」，而是「错了也伤不着、查得出、撤得回」。

12.3 机器管每一刀：判断链与四道关卡

标准是「要防住什么」，从这一节起看 dsh 怎么把它变成会跑的机制。分工一句话先立住：

▶分工口诀

机器管每一刀，你管抽查与拍板——模型只出主意、不是裁判；机器的活是四道关卡，你的活是三时点 + 六个旋钮（12.4 末尾清单）。

先堵一个常见误解：这条判断链上，模型不是裁判。模型只出主意——决定调哪个工具、传什么参数；它没有权力决定「能不能干」。能不能干，由代码和人分着判，各按各的准则：

谁在判判什么判断依据
模型（出主意）想干什么任务目标 + 工具说明书；无权判能不能
代码 · 沙箱（默认裁判）写哪个路径路径在不在允许范围——内核级规则，机械、可预测
代码 · 规则表（你写死的）工具名 / 参数hooks 规则、tools.restrict 名单
人 · 批准弹窗（你）这一刀放不放12.2 的三问：影响面 · 可逆性 · 可验证性
人 · 配置时（你）默认定在哪一档任务域的风险与信任

由此两条推论：模型永远说服不了代码放行——被拒只能换方案，判断权在模型之外；默认裁判是确定性规则——沙箱那句「越不越界」是操作系统在系统调用层执行的，可预测、不可绕过。

「机器管每一刀」的实体，是每次工具调用都要过的那道闸门。dsh 不靠 Agent 自觉，四道关卡：

关卡干什么说人话
tools/pre-execute 预检waterfall 事件（监听器排着队逐个过）上表态：允许 / 否决 / 询问三选一闸机
批准通道（ctx.approval）「询问」转人工：allowed-once 才放行；拒绝、取消、无人应答都算否决问主人
单调守卫（tools.guard()）只许否决、没有放行——拿到的只是只读快照，顺序怎么排都翻不了案一票否决
沙箱（sandbox-local）read-only / workspace-write / danger-full-access 三档活动范围；沙箱不可用直接拒，绝不悄悄放开划界

「询问」是谁点的？不是一份笼统的「危险操作清单」，而是两层可查的规则：

  • 按工具名匹配的规则表——dsh 桥接你现有的 Claude Code hooks 配置（hooks.json 或 settings 文件的 hooks key）：PreToolUse 规则按工具名匹配，跑你的命令，按输出表态 allow / deny / ask；多条规则串行执行、按最严格折叠（deny > ask > allow）。位置：cordis.yml 里 dsh-hooks-claude-code 的 configPath（如 ./.claude/hooks.json）；
  • 权限预设——dsh-permission-presets 把「沙箱模式 × 批准策略」打包成命名档（组合见下表「配套批准」列）；UI 一个选择器 / 一句 /permissionPresets 切换，defaultPreset 决定新会话默认；
  • 代码级——原生插件直接注册 tools/pre-execute 监听器表态三选一，或用 tools.restrict({allow, deny}) 按工具名圈白 / 黑名单——这是插件 API，不是配置文件（插件写法，第 14 章）。

沙箱这一档，三种模式拆开看——前两档是「墙」，第三档是「拆墙」：

模式能干什么机制上怎么强制配套批准
read-only 只读只能读；改动一律拒绝（只放行 /dev/null 这类被点名的空 sink）墙：内核文件策略（bwrap / Landlock / Seatbelt / ACL），写的那一刻拦截，不可绕过兜底默认（故障安全），不是预设选项
workspace-write 工作区工作区内 + 临时区可读写；工作区外仍拒墙：同一套内核机制，白名单 = 工作区根 + /tmp；越界即拒，想越界要升权ask（预设 workspace-write）
danger-full-access（Full access）绕过限制，敏感操作直接做拆墙：不做文件策略约束（bypass）——等于没有沙箱，不是墙更高never（预设 danger-full-access，无确认弹窗）
图 12-2 沙箱三档：前两档是墙——能写的地盘到墙为止，墙外被拦；第三档拆墙——没有墙。Full access 的「自动感」来自批准策略 never。
  • 判定维度只有文件效果——网络、进程可见性不在词汇表里（所以 Full access 也不管 git push）；
  • 升权是阶梯——只能往更宽升，且必须带理由走批准通道、一次一问、执行前裁决（被拒什么都没跑）；
  • 换挡有记录——会话级切换写进日志（sandbox/mode 事件）、会话创建时固定；强制完整度不足时报 partial，绝不悄悄降级为不受限。

两个默认值先记下：沙箱策略的兜底默认是 read-only（故障安全），批准策略默认 ask（无人应答则失败关闭）；而 dsh 的 web 版默认组合把它配成 workspace-write + ask（= 权限预设 workspace-write 这一档）。四道关卡的出处也可点开核对：pre-execute 与单调守卫、批准通道、沙箱三档。

回到直觉：「git 命令有些能用、有些不能用」——对，但默认不是按命令名分的，而是按文件效果分的，而且拦发生在「写的那一刻」（沙箱不分析命令，只给整个 bash 进程划好可写范围）：

git 操作默认（workspace-write）原因
status / diff / log放行只读，任何档位都能跑
add / commit放行写工作区内的 .git/ 与文件
写工作区外（如 config --global）拒 → 升权越界，写的那一刻被拦
push / fetch（网络）默认不拦文件沙箱不管网络

想按命令名细分（比如禁 git reset --hard），默认没有——要在 hooks 规则或插件里自己写（hooks 的 matcher 只到工具名 bash，命令参数要脚本自己读）。

两道关卡还互相咬合：想越出沙箱档位，得走批准通道升权——一次一问、只能往更宽的档升、批准了才生效；没批准，执行前就被拦下，什么都没跑。真实顺序：预检 →（询问）→ 守卫 → 沙箱（执行时最后一道）；一次调用的完整九道关，第 16 章 16.3 展开。这些关卡为什么能排队挂在调用前——事件与监听机制，第 15 章《让零件通风报信》。

⇄双线提示 · 创造线视角

这排关卡全是插件，挂在 waterfall 事件上——想拦什么，写个监听器就行（插件怎么写，第 14 章《把功能插上插头》；事件机制，第 15 章）。dsh 自己的子 agent 就装了单调守卫：结构化输出一交卷，后续工具调用一律拦下——第 18 章《一个人变一支队伍》里，子 agent 的工具箱就是这么圈起来的。

12.4 你管抽查与拍板：三时点、旋钮与调档

机器的半边是四道关卡（12.3），你的半边是三个时点 + 六个旋钮 + 信任调档。三个时点：

  • 查计划——动手之前：它打算干什么？路线对不对？
  • 查执行——过程之中：机器把守每一刀，你抽查日志里的关键几刀；
  • 查产物——收工之后：对着日志核对结果，哪些改对了、哪些要打回——第 9 章 9.4 的复盘三问（喂饱 · 看见 · 验证）就是收工后的标准动作。

「查计划」的现成工具是 plan mode（勘探模式）：一句 /plan 把 Agent 调进去——只调研、只设计，最后把完整计划交到你手里，你点头，它才动手（交出计划走 exit_plan_mode，批准了才退出）。看透它的性子，分两半：

  • 软引导——plan mode 本体只是一段引导文案加一道「交计划」的门，它自己不强制任何事；
  • 硬执行——真按住模型手的，还是沙箱与批准策略：plan mode 不碰它们。

计划状态也写进黑匣子（plan/mode 事件），第 9 章执行日志里查得到；这门怎么在循环里转——第 16 章《看心脏怎么跳》。

图 12-3 审查工作流：查计划、查执行、查产物三时点，配上执行的四道关卡——信任长在关卡上。

走一遍真实的控制旅程：你让 Agent 删掉一个工作区之外的文件（比如 ~/Downloads/x.txt），当前会话在 workspace-write 档下：

  1. 出主意——模型决定调 bash 执行 rm；
  2. 沙箱拦下——执行前按档位把关：这一刀越界，被拒。模型收到结构化消息 [sandbox: file access denied under workspace-write mode]，还附一句提示：带 sandbox_permissions（升到够用的最窄一档）+ 一句理由，原样重试一次，批准弹窗会问你；
  3. 申请升权——模型带理由重试，申请升到 danger-full-access；
  4. 你拍板——批准弹窗到你面前：升到哪档、为什么。你点头（allowed-once），这一刀放行；不答或拒绝，失败关闭，模型收到被拒的结果，继续想别的办法；
  5. 全程留痕——approval/asked 与 approval/decided 审计记录写进第 9 章的执行日志，复盘查得到。

全程你只做了两件事：点了一次头、扫了一眼日志。剩下的每一刀，机器都在把守。

注意两套三档别混：12.2 的三把钥匙，是你抽查多勤；这里的沙箱三档，是机制把墙砌多高。墙砌得矮，钥匙给得再大方也越不了界。

把「怎么控制」收成一张旋钮清单——机器有四道自动关卡（上表），你手里有六个旋钮：

你手里的旋钮管什么对应
/plan 勘探模式动手前的路线查计划
批准弹窗：点头 / 拒绝 / 不答危险与越界的每一刀查执行
文件策略三档 + 升权申请它能碰的活动范围沙箱
第 9 章执行日志 + 复盘三问收工后的核对查产物
AGENTS.md 写约定（如推送前跑 pre-push-checks）把把关固化成每次都做写回（8.3）
postmortem · lefthook · knip教训变成机器守门升降级 · 固化
▶产品形态实证

你在用的 dsh 会话里就写着两行——文件策略 workspace-write（沙箱第二档）、批准策略 ask：没有可用应答者时，请求失败关闭。本章的关卡不是概念，是你眼前正在跑的值。

被拦的这些坏消息，模型都看得见、循环照常转——取消与自救，第 16 章 16.4。

最后，标准里的「信任随战绩浮动」怎么落地？信任不是发一次钥匙就定终身：

  • 降级——出一次错，同类活降一档：全信 → 核查，核查 → 亲为。出错不丢人，装作没看见才丢人；
  • 升级——同一档连续可靠干满若干次，升一档。信任是挣来的，不是授予的；
  • 固化成护栏——吃过的亏，别靠人记着：把「必须查什么」写进复盘的约定里，让机器替你查。第 7 章的三位机器门卫就是样板——docs/postmortem/ 编号复盘把坑归档、lefthook.yml 与 knip.json 在提交口守门：dsh 自己就这么养自己。
图 12-4 升降级循环：定档 → 干活 → 查账本 → 复盘调档；教训固化成护栏，机器替你把关。

一张图总结

图 12-5 本章全景：危害（把关全拆）→ 标准（分级与守则）→ 机制（机器关卡 + 你的时点），再配升降级——信任是一套可校准的机制。

要点回顾

  • 危害：把关全拆 = 越界写、不可逆误操作、静默错误、信任不校准——都落在「影响大、不可逆、验证不了」的动作上；靠模型自觉兜不住。
  • 标准：防住它 = 划范围 + 问人 + 可查 + 可调 + 判断权在模型外；每件活先按三问分三档（全信 / 核查 / 亲为）。
  • 机制：机器管每一刀（预检 → 批准 → 守卫 → 沙箱；沙箱三档=只读 / 工作区 / Full access，前两档是墙、第三档拆墙），你管抽查与拍板（三时点 + 六个旋钮）；模型不是裁判、只出主意。
  • 升降级：出错降一档、连赢升一档；教训固化成机器守门（postmortem · lefthook · knip），不靠人记着。
  • 一条主线：信任不是态度，是可校准的机制——危害、标准、机制三步走。

动手做

  1. 做一次「拆掉一个」：挑一件 Agent 干的活，说出「如果没把关会怎样」（对照 12.1 危害表），再反推它该上哪条标准（对照 12.2 标准表）、该定哪一档。
  2. 做一次「故意越界」实验：让 Agent 删一个工作区之外的文件，看它撞上哪道关、你收到什么批准弹窗，再到第 9 章的执行日志里找 approval/asked 与 approval/decided 两条留痕；最后跑一句 /permissionPresets，看当前档位与可选预设表。
  3. 从 docs/postmortem/ 挑一篇复盘，指出它对应本章的哪一档调整、固化了哪道护栏。
