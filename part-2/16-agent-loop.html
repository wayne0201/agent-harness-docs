第 16 章 · 看心脏怎么跳

拆解 Agent 循环与工具管线，看懂引擎如何运转

第 15 章结尾问：谁来指挥模型一轮轮想、做、看？这一章看心脏——Agent 循环（第 1 章 1.5 心智模型里那个 Loop，在这里有了学名：ReAct）。第 8 章 8.2 的「模型出主意、工具动手」，在这一章放大成一次完整的搏动。先分清两种粒度，再走一遍主循环、拆一次工具管线，最后看它出错时怎么自救。全章一个比喻：心脏的搏动。

◆本章核心问题

Agent 到底怎么「转」起来？

▶你将获得

理解 Agent 运行时引擎，能定位每一步发生在哪。

16.1 想一步、动一手、看结果：核心循环的骨架

核心循环的骨架是：想一步 → 动一手 → 看结果 → 再想下一步。学名是 ReAct（Reasoning 思考 与 Act 行动 交替），出自 2022 年的一篇论文（ReAct: Synergizing Reasoning and Acting in Language Models，Yao et al. 2022）。第 8 章 8.2 的「模型出主意、工具动手」，就是它在单个任务上的样子；第 1 章心智模型里那个「循环」，就是它。

图 16-1 你说话触发一个回合，回合里 step 循环（想→动→看），中途产物随时落地，最终结果回到你。

在这个循环上，有两个通用概念，不依赖任何具体实现：

  • 回合（turn）——从你输入一句话，到 Agent 决定停下来。这是一整件事。
  • 步骤（step）——回合之内的一次「想 + 动 + 看」。一件事往往要好几个 step 才能干完。

一个回合里可以有好几个 step——模型觉得还没干完，就再来一轮。两种粒度各有用途：计费看 step，会话和断点看 turn。

那「什么时候停」？通用答案是：模型这一轮「不行动」了——它不再要求调用任何工具，说明它觉得干完了（或该把控制权还给你），回合就结束。图里那条「最终结果 → 你」的虚线，就是模型说停之后的事。

16.2 一次 step 的五阶段：从输入到去留

把「想一步、动一手、看结果」放慢，一次 step 走五阶段——每个阶段 dsh 都实现了，还给了具体名字（括号里是 dsh 的叫法）：

  1. 拿输入——取本步要处理的那批消息（用户说的、上一轮工具的结果）。一般是队列（先进先出）：对话要保序，先来的先处理；栈（后进先出）会打乱对话顺序。dsh 里的叫法：收件箱（inbox）＋认领（claim）——也是队列，等下个回合的消息从队头取一条，上一轮的工具结果整批取走。
  2. 拼提示——把系统提示、上下文、工具说明拼成发给模型的请求；有些引擎允许这一步被「拦截/注入/拒绝」。dsh 里的叫法：pre-step、system-prompt/assemble。
  3. 问模型——把请求发给模型，拿到它的回复。dsh 里的叫法：agent/request → llm/stream。
  4. 跑工具——模型说要调用工具，就执行（带护栏），把结果拿回来。dsh 里的叫法：tool/call → 工具管线 → tool/result。
  5. 定去留——看模型这轮「还要不要工具」：要 → 带着工具结果回到第 3 步再来一轮；不要 → 回合结束。dsh 里的叫法：turn-stopping 终检 → turn/end。
图 16-2 五阶段是通用引擎骨架，dsh 给每阶段起了名字：认领、装配、请求、工具、收尾。

看清了：「五阶段」是通用设计，dsh 只是证实它——通用概念「想一步 / 动一手 / 看结果」分别落在第 3、4 步和那条回边。

「停还是继续」怎么判定？看三点：

  • 判据——模型这一轮输出的 assistant/message 里有没有 tool-call 块（driver 的 step() 结尾）：
// 1. 看模型这轮输出里有没有工具调用
const toolCalls = message.content.filter(block => block.type === 'tool-call')

// 2. 没有 → 模型觉得干完了，回合结束
if (toolCalls.length === 0) {
  return { kind: 'completed' }
}

// 3. 有 → 执行工具，结果塞回「下一步」输入，进入下一 step
return concluded ? { kind: 'completed' } : null
  • 谁拍板——模型只「提案」（输出里带不带 tool-call），driver 代码按确定性规则判定；agent/turn-stopping（serial）在「模型说停 + 收件箱没新输入」时做最后一关复核——插件可以在这里拦下结束或放行（第 12 章「模型只提案、裁决在代码」的又一次落地）。
  • 安全阀——模型会一直「只要工具」地转下去（复杂任务拆多步），所以循环有兜底：max-tokens 截断、工具超时（16.4）、重复打转提醒，都是防止它无限转的安全阀。
⇄双线提示 · 应用线视角

你不写 driver，但「卡住」时得知道卡在哪：消息发出去没反应 → 卡在①（没被认领）；模型回了但没干活 → 卡在②③（提示没装配对）；工具调用了却没结果 → 卡在④（管线某关拦了）。定位到阶段，再去看对应事件，就是第 9 章日志的用法。

16.3 工具执行管线：一次调用的九道关

工具能干活，也能干坏事——所以调用必须有过护栏（权限、沙箱、超时、可拦截）。dsh 把「护栏」做到了极致：一次工具调用要过九道关（第 15 章见过它的三连站 tools/pre-execute / execute / post-execute，这里是完整版，依据 tool-execution-pipeline.zh.md）：

九道关按角色分三组（顺序见图 16-3 的蛇形走位）：

  • 三个 waterfall（可插队、可拦截）——tools/pre-execute（钩子、权限、沙箱）→ tools/execute（超时、重试、指标）→ tools/post-execute（接受、拦截、替换、附加上下文）；
  • 守卫与询问（可拍板）——单调守卫（只许否决/弃权、保护身份）→ ctx.approval（一次性询问，没回应=否决，第 12 章的主角）→ 工具主体（真正干活的代码）→ 文件守卫（fs 写改过 fs/write-intent、fs/edit-intent）；
  • 收尾三关（不可拦截）——finalizeContent（工具自声明的「仅内容不变式」）→ tools/result（冻结的权威结果，落成 tool/result 日志事件）。
图 16-3 工具执行管线九道关：三个 waterfall 加守卫、询问、主体、不变式、落账，一次调用九关全过才算数。

16.4 取消与错误恢复：心脏的自救

心脏会漏跳，循环也会。出错的应对是重试、超时、提醒三招。dsh 把这三招做成了三个插件，坏消息全部结构化：

  • 请求失败——模型调用出错，agent/request-error（waterfall）一响：llm-retry 按策略重试；若是上下文溢出，compaction-basic 先压缩再重开一轮（第 10 章的主角）。
  • 工具超时——工具声明自己的 timeoutMs，timeout-policy 在 tools/execute 上设一个截止信号；到点就把结果替换成结构化的 TOOL_TIMEOUT 错误。模型看到的是「超时了」三个字，而不是一个卡死的进程。
  • 重复打转——模型用完全相同的参数连调同一个工具，repeat-tool-reminder 数到 3、5、8 次就逐级注入提醒：「停一下，重读上次结果，换个方案」。它只提醒，不拦路。
图 16-4 心脏的自救：失败重试、超时报错、重复提醒——坏消息全部结构化，循环继续跳。
▶一句话记住

坏消息也要结构化。失败、超时、打转都是「正常输入」，循环从不假装没看见——它把坏消息变成一条消息，再交给模型决定下一步。

16.5 dsh 的特别设计：循环之外的匠心

通用核心讲完了，dsh 在循环本身之外，还有两处值得单独说一说的设计——它们不是「必须」，而是「锦上添花」：

图 16-5 dsh 的两处特别设计：循环本身全是插件接缝、每一步都可回放。

① 循环本身全是插件。通用 Agent 的循环常常是写死的一段代码；dsh 把五阶段、工具的每一道关、甚至「要不要停」的终检，全做成了 waterfall / serial / emit 接缝（第 15 章的机制）。于是「在任何位置插入逻辑」不只是口号——想给工具加审批，监听 tools/pre-execute；想改模型看到的提示，监听 agent/pre-step；想在回合结束时拦一下，监听 agent/turn-stopping。这是第 13 章「一切皆插件」在循环这个最核心的地方做到了极致。

② 每一步都可回放。很多 Agent 循环只是「跑一遍」，跑完就没了；dsh 让循环可重放——模型吐的每个分片先落执行日志（assistant/chunk），收件箱的待办也持久化（agent/inbox/spliced）。带来的两个好处：进程重启能从日志重放、不丢活；复盘时每一分片都在第 9 章的执行日志里，看得见 Agent 每一步是怎么想的。循环不只是「会跑的」，还是「能回看的」。

一张图总结

图 16-6 心脏搏动：舒张泵上下文给模型，收缩把结果泵回日志——循环即心跳。

要点回顾

  • 两种粒度：turn 是完整回合（你说话到它停），step 是一次搏动（进消息到出结果）。
  • 学名 ReAct：想一步 → 动一手 → 看结果——核心循环的骨架；五阶段是通用引擎骨架，dsh 用 driver 实现了它。
  • 主循环五阶段：认领 → 装配 → 请求 → 工具 → 收尾；每站都是插件 + 事件，回边是心跳。
  • 工具管线九道关：三个 waterfall 加守卫、询问、主体、不变式、落账——任何一环都能否决或改写。
  • 自救三层：失败重试/压缩、超时报结构化错误、重复打转逐级提醒；坏消息也要结构化。

动手做

  1. 开一次 dsh 会话，让 Agent 做一个小任务（比如改一个文件名）。任务结束后，凭记忆画出这次任务的五阶段，再对照 agent-lifecycle.zh.md 的时序图核对。
  2. 回忆这次任务里的一次工具调用，说出它过了九道关里的哪几关（至少说出 pre-execute、execute、post-execute、tool/result 四关）。
  3. 设想给「超时」加一条自定义策略：它该监听哪个事件？用哪种模式？为什么？（提示：拦截用 waterfall，参考 16.4 的 timeout-policy。）

心脏每跳一下，都留一道痕迹——assistant/chunk、tool/call、tool/result，一条条追加进执行日志（第 9 章）。痕迹攒起来，就是 Agent 看得见的过去。心脏的搏动看完了，下一章换个视角：换一个器官——看看 dsh 里哪些部件能整个换掉，接缝在哪。
