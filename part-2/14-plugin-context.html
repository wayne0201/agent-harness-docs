第 14 章 · 把功能插上插头

学会 Cordis 的插件与上下文，写出第一个插件

第 13 章结尾说：下一章 zoom in 到细胞——把「五个关键词」变成代码。这一章就兑现它。先写一个十行的插件，再认识 Cordis 的五个关键词，最后搞懂两件最让人挠头的事：谁先谁后（顺序与依赖）与拔掉插头（可逆效应）。全章一个比喻：插座与电器——上下文是配电箱，插件是电器，依赖是「用电要求」，效应是「拔掉插头，线收干净」。第 11 章抛过的悬念（技能系统在体内是怎么实现的）——本章用三个关键词当作活体标本剖给你看。

◆本章核心问题

「一切皆插件」如何在代码层面落地？

看懂并动手写一个 dsh 插件的能力。

14.1 第一个插件：十行代码的 hello

第 5 章问过三个哲学问题——怎么拼、先拼谁、谁说了算。答案落在代码上，就是下面这十行（取自 dsh 的 Cordis 教程，原文见 deepseek-harness/docs/cordis-tutorial/01-first-plugin.zh.md）：

import type { Context } from '@deepseek-ai/cordis'

export const name = 'hello'

export function apply(ctx: Context) {
  console.log('hello from my first plugin')
}

逐行看，只有三个要点：

  • apply(ctx) 是插件的唯一入口——框架加载你时，只调这一个函数；
  • ctx 是上下文——就是你插上插头的那个配电箱，之后你所有的「贡献」都登记在它上面；
  • name 只是诊断标识，可写可不写。

配套还有一份清单 cordis.yml：

- name: './hello.ts'

清单写「要挂哪些插件」，插件写「自己贡献什么」。启动器读清单、把每个插件挂到根 Context 上，挂到 hello 时调用你的 apply(ctx)——屏幕打出 hello from my first plugin。

图 14-1 最小插件的三动作：清单点名、Loader 并发挂载、apply(ctx) 通电——框架不「拉」任何东西。

注意最后一格：全程没有框架启动代码。插件不「拉起」任何东西，只描述自己的贡献；谁组合、谁启动，由清单说了算。dsh 自己的 packages/bundle/base 就是一份更长的插件清单（第 13 章的依赖主干就长在这份清单里），配置覆盖它——这正是第 5 章「谁说了算」在代码里的样子。

⇄双线提示 · 应用线视角

就算你一辈子不写插件，这份清单也天天见：在 dsh 里选模型、开关能力、改配置，本质都是在改这份插件组合。改完不生效时，第一件事就是查你的改动「挂上了没有」——多半停在 PENDING（14.3 会讲）。

▶插件有三种形态

函数（刚写的这种）、带 apply 方法的对象、以及 Service 子类。在需要对外提供服务之前，函数形态就够用——14.3 你会看到类形态何时上场。

14.2 五个关键词：Cordis 的全家福

十行代码背后，是 Cordis 的全部思想。dsh 的官方入门文档把它浓缩成五个关键词——第 13 章 13.2 里「Context 三样东西」（服务、事件、效应）的完整版：

  1. 插件（Plugin）——实现服务的对象：可以是一个带 apply(ctx) 的函数，也可以是一个类。在 dsh 里，连 Agent 循环本身都是一个插件。
  2. 上下文（Context）——服务的仓库：每个服务挂在一个稳定的 ctx.xxx 键上（ctx.llm、ctx.tools、ctx.sessions），插件按「键」找服务，而不是 import 某个具体实现。
  3. 依赖注入（inject）——插件声明自己需要哪些服务；框架保证「所需服务就绪后才挂载它」。加载顺序由依赖关系自然表达，不需要手工排启动顺序。
  4. 类型化事件（Typed Events）——插件之间靠事件通信，五种派发模式各司其职：emit（广播观察）、parallel（并发执行）、serial（串行执行）、bail（serial 的同步版）、waterfall（接力包装）。
  5. 可逆效应（Effects）——一切注册（提示分区、工具 schema、适配器、监听器）都通过 ctx.effect() / ctx.on() 进行；卸载或热重载时，效应按预期有序收回。
图 14-2 五个关键词围着配电箱：插件提供服务、依赖决定顺序、事件负责通信、效应保证可逆。
关键词它是什么生活说法一句记忆
插件实现服务的对象电器一切功能都是它
上下文服务的仓库配电箱按键取服务，不 import 实现
inject依赖声明电器的用电要求所需服务就绪，它才通电
事件类型化通信广播线路五种播报方式（第 15 章）
效应可逆的注册保险丝 + 插头拔插头，线收干净

五个关键词里，事件的五种派发模式本章只点到名字——第 15 章《让零件通风报信》会逐一带你试播。依赖与效应，则是本章后两节的主角。

走一遍活体标本：技能系统的体内实现

第 11 章结尾留了个悬念：技能在体内是怎么实现的？答案是三个插件，把五个关键词挨个用了一遍。你已经在第 11 章用过它们（拆锦囊、看目录），现在从「创造」这一侧看同一套东西：

插件inject 谁干什么用到的关键词
dsh-skill—提供 ctx.skills 注册表：不知道技能从哪来，只等提供方来 registerProvider服务 + 上下文
dsh-skill-filesystemskills扫描 .agents/skills 解析 SKILL.md，把每个锦囊注册成提供方插件 + inject
dsh-tool-skillagents · tools · skills发布第 11 章那个 skill 工具：渲染目录、按名加载 SKILL.md 原文插件 + 服务 + 效应

三条线合起来就是你在第 11 章看到的全部：注册表（服务）等提供方来注册，文件系统插件（inject 声明它要注册表）去发现并注册，工具插件（又要注册表、又要工具表）把目录和正文端上桌。它们没有一个在「启动时一次性搭好」，全靠 inject 声明 + 注册效应——这就是「注册即效应」在 dsh 里的真实样子。

⇄双线提示 · 应用线视角

第 11 章你只关心「拆开能用」；现在你看到它底下是三块插件拼的。下次技能「不出现」，你知道去哪查：注册表有没有提供方（dsh-skill）→ 文件系统有没有扫到（dsh-skill-filesystem）→ 目录有没有上桌（dsh-tool-skill）。

科普小站：插件化思想的简史

「把小工具组合成大系统」是条老路：Unix 管道让一个程序的输出成为另一个程序的输入；微内核把操作系统的大部分功能挪出内核、做成可装卸的模块；再到前端生态里处处可见的 plugin 体系。Cordis 做的，是把「一切皆插件」从一种风格变成一个运行时内核——插件不仅可装卸，而且装卸是可逆的、顺序是由依赖算出来的。第 5 章的「时空可组合性」，就是这套内核的哲学表达。

14.3 顺序与依赖：谁先谁后，谁说了算

第 13 章在依赖主干里看到一句话：「行序不承载加载语义，激活由服务可用性驱动」。这一节把这句话拆开——为什么不用手工排顺序？Cordis 用两条铁律回答：

  • 铁律一：注册顺序 = 默认顺序。没有依赖声明的插件，按注册顺序依次运行。
  • 铁律二：有依赖声明，就按依赖来。插件声明 inject: ['llm', 'tools'] 之后，框架保证这两样就绪之前它绝不运行——与它注册得早还是晚无关。

背后是一个状态机，每个插件实例（fiber）在其中流转：

PENDING → LOADING → ACTIVE → UNLOADING → DISPOSED
                 ↘ FAILED

PENDING：依赖没齐，先等着——「为什么我的插件没输出」，最常见的答案就是它。LOADING / ACTIVE：apply 正在跑 / 已就绪。FAILED：apply 或配置校验抛异常。UNLOADING / DISPOSED：正在拆除 / 拆完。

用教程里的例子看一遍。greeter 插件提供一个问候服务，consumer 插件声明 inject: ['greeter'] 再消费它：

export class GreeterService extends Service {
  constructor(ctx: Context) { super(ctx, 'greeter') }
  greet(who: string) { return 'Hello, ' + who + '!' }
}

export const name = 'consumer'
export const inject = ['greeter']
export function apply(ctx: Context) { console.log(ctx.greeter.greet('world')) }

把清单里两行的顺序对调，输出不变；把 greeter 那一行删掉，consumer 就静静停在 PENDING——不崩溃，也不半吊子运行。谁先谁后，不是排出来的，是依赖声明让框架算出来的。

⇄双线提示 · 应用线视角

「我的插件没反应」是 dsh 用户最常见的问题之一，答案多半是 PENDING：它依赖的服务还没就绪。机制是创造线的，诊断它的能力属于每一位使用者——第 13 章那张依赖主干表，就是你排查时的地图。

更妙的是，这份依赖是持续跟踪的，而不是启动时检查一次就完事：

  1. 提供者 A 挂载，交出 ctx.llm → 所有 inject: ['llm'] 的插件被唤醒，自动激活。
  2. A 被卸载（它的效应全部收回）→ 依赖者们自动卸载——disposer 按注册的逆序执行，像叠盘子：后装的先拆，先装的后拆。
  3. 换上新版本 A′ → 依赖者们自动重载，重新拿到新实现。
图 14-3 提供者与依赖者的生命周期联动：A 的挂载与卸载，自动驱动 B 的激活与重载。
▶一句话记住

「先注册谁」不重要，「谁依赖谁」才重要——顺序是声明出来的，不是排出来的。这也是 dsh 能「一次替换，全产品改变」的地基（第 17 章会站在这个地基上看接缝）。

14.4 可逆效应与类型安全：拔插头与说明书

插件装上后还可能被卸载：改配置、热重载、依赖消失，都会触发拆除。所以 Cordis 要求：一切注册都必须可逆。

凡是 Cordis 认识的注册——ctx.on() 监听事件、ctx.plugin() 挂子插件、服务注册——本身就已经是效应，卸载时自动撤销，你不用管。只有 Cordis 不认识的资源（定时器、网络连接、文件 watcher），才需要亲手包一层：

export function apply(ctx: Context) {
  ctx.effect(() => {
    const timer = setInterval(() => console.log('tick'), 200)
    return () => { clearInterval(timer); console.log('cleaned up') }
  })
}

ctx.effect() 里跑的是「装」的逻辑，return 的那个函数是「拆」的逻辑（叫 disposer）。拆的时候按注册的逆序执行——后装的先拆，先装的后拆，就像收盘子从上往下拿。

图 14-4 叠盘子：注册正序 ①②③，卸载逆序 ③②①——后装的先拆，垫底的最后拆。

最后是类型安全。运行时，greeter 用 super(ctx, 'greeter') 把服务挂到键上；编译时，还有一行不起眼的声明合并，让 ctx.greeter 到处都有类型提示：

declare module '@deepseek-ai/cordis' {
  interface Context { greeter: GreeterService }
}

这行不生成任何代码；没有它服务照样能跑，但消费方会失去编译期检查。配电箱每个插孔的规格都写在说明书上——服务键是运行时的事实，声明合并是编译时的说明书，两边对得上，才敢放心插拔。这也正是第 13 章那句「替换只看接口」的机制基础：接口（键 + 类型声明）就是说明书。

展开一层，回答一个常见疑问：A 插件依赖了 B 插件，它从类型上是怎么知道 B 有什么方法的？不是 A 去 import B 的实现——而是两段各管一段：

  • inject 管运行时——A 声明 inject: ['b']，框架保证 B 的服务在 A 激活前已就绪（14.3 的状态机），这只是「运行时存在」的保证，不含任何类型信息；
  • 声明合并管编译时——B 用 declare module '@deepseek-ai/cordis' 把自己的服务类型塞进全局 Context 接口，A 里写 ctx.b.someMethod() 就有自动补全和类型检查，全程不用 import B 的实现类。

真实案例：dsh 的模型服务 ctx.llm 就是这么声明的——packages/llm/llm/src/index.ts 里一行 interface Context { llm: LlmRuntime }，消费方声明 inject: ['llm'] 后直接调 ctx.llm，背后挂哪个适配器它一概不知（第 13 章「替换只看接口」的活例）。想看最小完整版，教程 03-services.zh.md 里 greeter 与 consumer 的完整代码就在那。

回头再看 14.2 的技能家族，三块插件各自声明 inject、各自用 ctx.effect 注册——把「注册即效应」走了一遍。到这里，你会看插件、会判断依赖、会收拾效应，已经具备了动手写自己插件的基础——第 20 章《设计一个好工具》再教你把它设计得让模型好用。

一张图总结

图 14-5 插座与电器：写插件、通电、拔插头——五个关键词各就各位。

要点回顾

  • 插件只有一个入口：apply(ctx)，一切贡献都登记到上下文上。
  • 上下文是服务的仓库：每个服务一个稳定键（ctx.llm、ctx.tools…），按键取服务，不 import 实现。
  • 顺序是算出来的：注册顺序是默认，依赖声明是覆盖；依赖持续跟踪，提供者换人，依赖者自动卸载重载——第 13 章那句「行序不承载加载语义」就是它。
  • 一切注册可逆：效应卸载时逆序收回，后装的先拆；技能系统就是「注册即效应」的活体标本。
  • 声明合并给类型：运行时挂键 + 编译时声明，插孔规格有据可查——接口（键 + 类型）就是说明书。

动手做

  1. 打开 01-first-plugin.zh.md，跟着写一遍 hello 插件；没环境也没关系，在纸上写出 apply(ctx) 里你要做的那一件事。
  2. 在 deepseek-harness/packages 下任选一个插件，找它的三个痕迹：inject 了谁、提供了什么服务、注册了哪些效应（对照 14.2 技能家族那张表来找）。
  3. 设想你要写的一个插件，回答三问：它提供什么服务？它依赖谁？卸载时它要收走什么？

插件都挂上了、顺序也理顺了，可插件之间怎么说话？广播、传阅、还是排队？——下一章《让零件通风报信》，我们把配电箱里的广播线路接上电。
