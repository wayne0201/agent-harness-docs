第 9 章 · Agent 的执行日志

Agent 的执行日志——复盘、调试、审计的第一现场

第 8 章结尾说：干活的每一步都被记进一份执行日志——界面上叫「Session log」（会话日志），也就是我们说的黑匣子；干岔了怎么办、日志怎么读。这一章就打开它。全章一个比喻：飞机的黑匣子——飞行中你感觉不到它，出事时它救你。记忆线上它是「记录」一站：第 7 章提供（记忆放进文件）→ 本章记录（过程落成日志）→ 第 10 章消费（喂回模型）→ 第 8 章写回。

◆核心问题

干岔了怎么办？Agent 的执行日志记了什么、怎么读？

▶你将获得

会读 Agent 的执行日志：复现问题、回放过程、为验收取证。

9.1 为什么要有执行日志：先记后用

先问为什么：为什么要记日志？因为 Agent 干活的每一步——你的消息、模型的每个分片、工具的每次调用、喂进去的交接框——本来都是转瞬即逝的。干得顺，没人回头看；一旦干岔，没有记录，你就只能对着最后的结果猜「它刚才看见了什么、做了什么」。

所以日志的第一条规矩是先记后用：每一件事发生之前，先落成一行记录，再让下一步继续。飞机的黑匣子为事故留证据，dsh 的日志为复盘、审计、续写留证据——你平时感觉不到它，出事时它救你。

它长什么样：追加式 JSONL

具体地，它是一份 JSONL（每行一条 JSON 记录），由 session-persistence-jsonl 落盘：

  • 每个会话一个文件，默认 session.jsonl.zstd（zstd 压缩 + 校验和帧；关掉压缩就是纯文本 session.jsonl）；
  • 第一行是不可变的会话头：版本、会话 id、工作目录、agentPreset（恢复时用哪套工具与提示）、delegationDepth（子会话层级，顶层为 0）——第 7 章机器记里的格式版本化，管的正是这份文件；
  • 之后每一行一条记录，按发生顺序排成一条线，序号连续；
  • 日志放在 DSH_SESSION_ROOT 环境变量对应的路径下——部署没设这个变量时，用各自部署的默认位置。

它只追加、不自动清理——当得起「黑匣子」，正因为没有人偷偷删它；存多久是部署策略，不是机制。想取一份出来看，界面上「Session log」按钮会把日志打成 ZIP 交给你。

一条最普通的干活回合，在日志里长这样：

{"type":"session","version":0,"id":"…","agentPreset":…}             ← 会话头
{"type":"turn","subtype":"start"}
{"type":"user","subtype":"message","content":"给 tool-todo 加一个工具"}
{"type":"assistant","subtype":"chunk","content":"我先翻一下现有代码…"}
{"type":"tool","subtype":"call","name":"read","args":{"file_path":"…"}}
{"type":"tool","subtype":"result","name":"read","result":"…"}
{"type":"assistant","subtype":"chunk","content":"…"}
{"type":"tool","subtype":"call","name":"edit","args":{…}}
{"type":"turn","subtype":"end"}
（示意 · 字段从简）

对照第 8 章：干活小循环里的每一次「读、写、验」都留两行——tool/call（叫了谁、传了什么参）与 tool/result（回了什么）；交接框（system-reminder）也是先落日志、再进请求，第 8 章的交接在这份文件里看得见。

两个细节值得记住。一是打包分片：模型吐字是一个字一个字来的，连续至少 3 个同块 assistant/chunk 会合并成一行「打包行」，真实编程会话的日志因此小约 60%，读的时候无损还原。二是崩溃恢复：突然断电，日志尾部的半行被截断，读取器保留有效前缀、补齐结尾的收尾事件——宁可留一条带补丁的真相，也不丢一段有效历史。

图 9-1 日志条目流：会话头打底，事件一行行追加；分片打包省空间，崩溃恢复保真相。

9.2 一条不变量：模型可见 ⟺ 已记录

黑匣子为什么可信？因为它守着一条不变量：

◆全书心法 · 执行日志

凡是模型看得到的，一定先落了日志；凡是日志里的，都能完整重放。

先记后用，不是用了再补。

看两个方向：

  • 模型可见 ⟹ 已记录——你的消息、注入的指令、模型的每个分片、工具的每次调用与结果，都是先追加进日志、再进入下一步；分片「绝不丢弃」，连空内容都留一条记录；
  • 已记录 ⟹ 可重放——日志就是「发生了什么」的完整剧本：按序读一遍，就等于把那次会话原样重演。调试靠它复现，审计靠它取证，续写靠它恢复。
图 9-2 不变量：模型上下文是日志的子集；删掉日志，回放、审计、续写同时蒸发。
⇄双线提示 · 创造线视角

这条不变量不是 dsh 的专利——你给自己的 Agent 装黑匣子，照抄两句：只追加、先记后用。审计、回放、信任，全都建立在这条不变量上。

9.3 一份执行日志，五种派生

黑匣子只有一个，读它的人各取所需。日志之上，dsh 长出一批派生视图——全部只读日志，绝不另造真相：

派生包一句话作用
历史session-projection把事件投影成「模型可见的历史」——回放与续写读它
压缩compaction-basic历史太长时生成摘要，摘要本身也追加进日志
恢复session-checkpoint-policy断点策略：决定在哪些边界留「从这里继续」的锚
遥测session-telemetry用量、成本、时长的计量，可接 OTel 后端
标题session-title用模型给会话起标题——「日志背书的标题」
图 9-3 一份执行日志，五种派生：历史、压缩、恢复、遥测、标题——全部只读日志，可随意重建。

会话列表里的标题、用量面板里的数字，都不是「另存了一份数据」，而是从同一份日志现算出来的——日志删了，它们全消失。历史与压缩两路，正是下一章的主角。

那什么时候用得上它？人和 Agent 都要用，而且互相成全：

  • 人用它——复盘排障（9.4 的复盘三问）、验收取证（Agent 说改好了，日志里核对它真做了什么——第 12 章）、算账（遥测：用量、成本、时长）；
  • Agent 用它——日志就是它自己的记忆：历史投影续写上下文、压缩熬高汤（第 10 章）、断点恢复接着干；
  • 人和 Agent 一起用它改进项目——从日志复盘出的教训写回 AGENTS.md 与 notes（第 8 章写回），下一次开工自动上桌。dsh 自己就是这么养自己的：第 7 章事故档案员的 postmortem，源头也是日志。

于是日志有了公私之分：日志留在本地，教训走进仓库——复盘出的约定写进 AGENTS.md / notes / skills，随 git 交给全队；过程日志留在各自的 DSH_SESSION_ROOT 路径下，不随项目提交。想看别人出问题的现场，让对方把那一次的日志分享给你（「Session log」导出的 ZIP 发过来就行），你拿过来照 9.4 的复盘三问分析。你是 Agent 的使用者，它是复盘现场；你是 Agent 的开发者，它就是调试你作品的现场——第三幕会常回来找它。

9.4 复盘实操：从执行日志定位问题

接着第 8 章的例子走一遍复盘。你让 Agent 在 packages/ 下写一个新工具插件，它交出的代码没按手册的导出规矩来。别急着骂模型——打开黑匣子，按复盘三问查：

  1. 喂饱了吗？——看交接框：日志里的 system-reminder 段，有没有 packages/AGENTS.md 那一份？第 8 章说过：开工时工作目录在根，子目录的手册要「走到地盘」才补。没喂到，就不是模型笨，是上下文没喂饱；
  2. 看见了什么？——看读：tool/call 里它 read 了哪些文件、tool/result 返回了什么，有没有读错文件、读到半截；
  3. 验了吗？——看回炉：bash 跑测试的结果红没红，红了之后模型改了什么。

对位到日志行，三问各有一处「证据现场」：

{"type":"user","subtype":"message","content":"<system-reminder>… Instructions from: AGENTS.md …"}  ← ① 交接框里只有根那一份
{"type":"tool","subtype":"call","name":"read","args":{"file_path":"packages/AGENTS.md"}}      ← ② 它自己补翻了吗
{"type":"tool","subtype":"result","name":"bash","result":"✗ 1 failed"}                         ← ③ 验：红了
（示意 · 字段从简）

三问查完，多数「模型犯蠢」都会现出原形——不是模型不会写，是它没被喂到、没看到、或没验到。这正是第 6 章「出错先查边界与上下文」在科学篇的落地：先查上下文，再动提示词。

图 9-4 复盘三问：喂饱了吗 · 看见了什么 · 验了吗——三问各对位一处日志证据，查完再动提示词。
▶一句话记住

黑匣子记录的是「发生了什么」，不是「谁错了」。它不怪任何人，只给证据。复盘的习惯：每次干岔，先日志，后结论。

一张图总结

图 9-5 黑匣子全景：一份只追加的日志，同时喂养记忆、审计与派生视图。

要点回顾

  • 追加式日志：会话头打底、事件按序追加；分片打包省空间，崩溃恢复保有效历史。
  • 一条不变量：模型可见 ⟺ 已记录——先记后用，日志是完整剧本。
  • 五种派生：历史、压缩、恢复、遥测、标题，全部只读日志、可重建。
  • 复盘三问：喂饱了吗 · 看见了什么 · 验了吗——先查上下文，再动提示词。

动手做

  1. 用「Session log」按钮下载一份你自己的会话日志 ZIP，解压读前几行，认出会话头与第一条事件。
  2. 从日志里复述这次会话的前三步：谁先说话、模型回了什么、工具做了什么。
  3. 拿一次「Agent 干岔了」的真实经历，用复盘三问在日志里定位一步——先下结论：是「上下文没喂到」，还是「模型真错了」？定位后把教训写成一条 AGENTS.md 约定（哪怕一行），下次开工看它有没有自动上桌——你就完成了一次「用 → 写 → 长」。

日志记录一切，可记录不是为了供着——下一步看这些记录怎么被喂回 Agent。记忆线的「消费」一站，第 10 章《记忆是这样被读取的》。
