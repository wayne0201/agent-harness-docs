第 17 章 · 换一个器官

设计可替换的能力接缝，让系统可插拔

第 16 章我们盯着心脏看它怎么跳。这一章把视线从心脏移开，落在身体的接缝上——哪些部件能整个换掉，怎么换，换了之后别处怎么不受牵连。第 13 章埋过线：ctx.llm 是接口，背后挂哪个适配器由配置说了算；第 14 章铺好地基：按键找服务、依赖持续跟踪，提供者换人、依赖者自动重载。这一章把这条线拉直：接缝是什么、dsh 里有哪些真接缝、一次替换如何改变全产品、什么时候你该给自己设计一条接缝。全章一个比喻，接着第 5 章的乐高积木。

◆本章核心问题

如何让能力可替换，而不改动核心？

▶你将获得

设计「可插拔能力」的方法论。

17.1 接缝与三角色：凸点、积木、搭积木的人

乐高好玩，是因为所有积木的凸点尺寸统一：任何一块都能被另一块替掉，而整个模型不会散架。软件里的「凸点」叫 接缝（Seam）——一个能力的接口与它的实现之间那道缝。缝的两侧，谁也看不见谁。

站在缝边上的是三个角色（正是第 14 章「按键找服务，不 import 实现」的升级版）：

  • 能力定义（Service Definition）——凸点本身：这个能力「能做什么」的接口约定，在 dsh 里就是 ctx.xxx 上的服务；
  • 提供者（Provider）——积木内部：真正干活的实现，注册到凸点上，可以有多个、可随时换；
  • 消费者（Consumer）——搭积木的人：只通过凸点用能力，不知道也不关心是谁在实现。
图 17-1 三角色：消费者认凸点（ctx.llm），提供者交实现（deepseek / pi-ai），谁换谁都不惊动对方。

缝的价值在于：实现会过时、会变贵、会被更好的取代——接口应该比实现长寿。搭积木的人手里握着凸点标准，今天换这块、明天换那块，模型照样严丝合缝。

这套三角色不是 dsh 的发明——Claude Code、LangChain、CrewAI 换模型、换记忆、换工具时，靠的也是同一套角色。dsh 只是把每个角色都做成了插件，名字叫 ctx.xxx。这一章后面全是它的具体样子，但请记住：换器官这件事，任何 Agent 应用都会遇到。

17.2 dsh 里的真实接缝：一张替换清单

先别急着看 dsh 的键名——任何 Agent 应用都有几个必换件：

  • 模型——同一个能力可以换不同模型跑（换厂商、换大小、换成本）；
  • 记忆 / 存储——会话与状态落盘在哪（文件、数据库、内存）；
  • 工具——Agent 能碰什么（本地命令、外部 API、浏览器）；
  • 执行环境——代码在哪儿跑（本机、沙箱、云端容器）。

dsh 没发明这些可换件，它只是给每个都开了一道缝、起了名字：ctx.llm、ctx.sessionPersistence、ctx.tools、ctx.subprocess。仓库里有一张官方清单 docs/capability-seams.zh.md，摘几处最典型的：

接缝（ctx 键）能力现成实现换掉会怎样
ctx.llm模型调用llm-deepseek · llm-pi-ai · llm-replay换模型 / 换成回放，全产品跟着变
ctx.sessionPersistence会话落盘jsonl · sqlite换存储格式，回放与查询不动
ctx.subprocess进程执行subprocess-local · subprocess-e2b本机执行变远程隔离，bash / 终端 / LSP 跟着搬家
ctx.credentials凭据管理credentials-local换密钥来源
ctx.storage存储中枢storage-json · storage-sqlite换存储引擎
ctx.sessionTelemetry会话遥测session-telemetry-otel换观测后端

注意 llm 那行：llm 包本身身兼两职——既定义接口，又是消费者（组装流式分片，第 16 章的心脏就靠它）；llm-deepseek、llm-pi-ai 是提供者，注册到 ctx.llm 上；llm-retry（重试）、token-meter（计量）则是独立消费者，只监听事件、不碰实现。一个接缝养活五个包，各自只认自己的角色。

图 17-2 接口与实现分离：消费者与提供者隔着 ctx.llm 互不相识，换模型只动右侧一行。

上面这些接缝都在「进程内」——换的是同一进程里的实现。dsh 还留着一个向「进程外」的接缝：MCP（Model Context Protocol，模型上下文协议），行业标准的外部能力接缝（官网：modelcontextprotocol.io）。第 11 章预告过它，这里兑现：dsh 的 packages/mcp/mcp-client 是它的早期形态——接一个外部 MCP 服务器，把它列出的每个工具注册到 ctx.tools，模型当原生工具用，名字形如 mcp__服务器名__工具名（与 Claude Code、Codex 同一套形状）。

维度dsh 插件接缝MCP 接缝
缝在哪进程内：ctx.xxx 服务键进程外：标准协议（stdio / HTTP）
谁来接dsh 插件（llm-deepseek 等）任意 MCP 服务器（GitHub、浏览器…）
换什么换实现，不换接口换服务器，工具名自动带前缀
成本要懂 dsh 的 Cordis只需实现标准协议

两种接缝不是对立的：dsh 插件接缝管「进程内换实现」，MCP 管「进程外接生态」。想给 Agent 加一个 dsh 没有的工具，最快的一步往往不是写插件，而是挂一个现成的 MCP 服务器。

17.3 一次替换，全产品改变

缝的威力，要用一次真实的替换来感受。dsh 的 subprocess 家族（packages/subprocess/README.zh.md）管着进程执行：subprocess-local 在本机开子进程，subprocess-e2b 则把执行整个搬进 E2B 远程沙箱（e2b 家族说明见 packages/e2b/README.zh.md）。

为什么换掉一个提供者，bash、终端、LSP 会一起搬家？因为这三个消费方都不自己开进程——它们把执行环境的所有操作委托给 ctx.fs 和 ctx.subprocess 两个接缝（官方文档原话：现有实现「无需 E2B 专用 fork」）。于是你只做一件事：在配置里把本地方案换成远程方案，三者涉及可变状态的工作就都发生在同一个远程沙箱里了。

图 17-3 一次替换，全产品改变：换掉 subprocess 提供者，bash、终端、LSP 跟着搬家，其余环节纹丝不动。

把 dsh 的名字摘掉，这个实验就是每个 Agent 应用都会做的一件事：把执行环境从本机换成云端——本地跑、容器跑、远程沙箱跑，命令、终端、代码补全一概不知道差别。换的不是「某个产品」，而是一道标准接缝。

⇄双线提示 · 应用线视角

你不写插件，但「换个模型、换个执行环境，整个 Agent 就跟着变」正是你每天在用的体验——改个配置就是换器官。看懂接缝，你就知道哪些部件能放心换、换了会影响谁。

17.4 何时为一个能力设计接缝

看到这里你可能想把所有东西都做成接缝。别急——接缝有成本：多一层接口、多一份文档、多一处间接。缝要开在「会变的地方」，而不是到处开。

三个信号，命中一个就该开缝：

  1. 环境会变——本机 vs 远程、开发 vs 生产、单机 vs 集群（subprocess、存储）；
  2. 实现可选——同一个能力有多个正当实现，用户各有偏好（模型、落盘格式）；
  3. 测试要换——测试时想换成假实现或回放（llm-replay：把真实模型调用录下来重放）。
图 17-4 接缝判断：三个信号中一个就开缝；都不中就先写死，不为想象的变化买单。
▶一句话记住

缝开在会变处。判断标准不是「这个东西重不重要」，而是「这个东西变不变」。重要的不变之物，写死反而更清晰。这套判断不挑框架——换模型、换记忆、换执行环境，任何 Agent 应用都适用。（怎么把接口设计得让模型用得好，第 20 章《设计一个好工具》再展开。）

一张图总结

图 17-5 乐高全景：消费者、凸点、积木三角色 + 开缝三信号 + 替换的威力。

要点回顾

  • 接缝 = 接口与实现之间的缝：三角色各司其职——定义（凸点）、提供者（积木）、消费者（搭积木的人）。
  • dsh 把会变的能力全开成缝：ctx.llm、ctx.sessionPersistence、ctx.subprocess、ctx.credentials…各配多个实现。
  • 一次替换，全产品改变：换掉 subprocess 提供者，bash、终端、LSP 一起搬家，消费方零改动。
  • 进程外还有一条缝：MCP 让 dsh 接整个外部生态，与进程内接缝互补。
  • 缝开在会变处：环境会变、实现可选、测试要换——中一个就开；都不中先写死。

动手做

  1. 打开 docs/capability-seams.zh.md，挑一个你没见过的接缝，说出它的定义、提供者与消费者。
  2. 列出你手头项目里「最想换掉的一个能力」（存储？模型？执行环境？），用三信号判断它该不该开缝，为它起一个 ctx.xxx 键名。
  3. 设想给这个缝写一个「假实现」（像 llm-replay 那样），说说测试会因此变简单多少。

会换一个能力，就敢动手改一个 Agent。可一个人忙不过来时，换多少个零件也没用——下一章《一个人变一支队伍》：从主厨到后厨团队。
